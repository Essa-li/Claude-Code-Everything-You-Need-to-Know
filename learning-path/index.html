开始第 1 课

开始前：开好两个终端窗口

每一步开头都有一个标签，告诉你这一步在哪里操作：

窗口 A · Claude Code运行 claude 后进入的会话。在这里输入 /status 这类斜杠命令，以及要对 Claude 说的话。
窗口 B · 普通终端打开在同一个文件夹，用来运行 git、npm、cat 等命令。
编辑器用来修改文件，例如 TextEdit 或 VS Code。
只看不用输入，看清楚屏幕上出现了什么、想清楚再往下做。

本页按 Mac 编写。中级课程要求 Mac、Linux 或 WSL 2；用 Windows 的话，请对照英文原课。

准备清单

  1. 付费 Claude 套餐（Pro、Max、Team 或 Enterprise），或者 Claude Console 账号。免费套餐不包含 Claude Code。
  2. Mac 上装好 git 和 Node.js LTS：在终端运行 git --version 和 node --version，都能打印出版本号就行。
  3. 打开 claude-code-practice，点 Use this template → Create a new repository，建一个你自己的练习仓库，再克隆到电脑上。所有练习都在这个仓库里做，碰不到你的真实资料。
  4. 练习都在练习仓库里的 project/ 文件夹中进行。在下面填写练习仓库在电脑上的路径，之后每课的命令都会自动换成你的路径。
练习仓库是 11 月以前建的？

旧练习仓库没有 project/ 文件夹，带练程序也不一样。最简单的办法是按上面第 3 步重新建一个。想保留旧仓库的话，在它的文件夹里依次运行下面四条命令升级（命令来自原仓库 README）：

git fetch https://github.com/wesammustafa/claude-code-practice main
git checkout --no-overlay FETCH_HEAD -- checks capstone learn
git checkout FETCH_HEAD -- .github/workflows/progress.yml .gitattributes
node checks/upgrade.mjs

掌握路径

练习仓库里还有一个官方的英文带练程序：在窗口 B 的练习仓库里运行 npm run learn，Claude Code Quest 会在浏览器里打开，内容和本页对应，可以对照着用。本页的进度只保存在这台设备的浏览器里。

第 1 课 / 共 8 课 · 初级 · 约 20 分钟

安装、登录、熟悉界面

学完这课，你能装好 Claude Code，在仓库里安全地启动它，在它回答到一半时叫停，说出当前会话用的是哪个模型和账号，并且会拿代码去核对它说的话。

先看约 85 秒的配音演示动画，再跟着下面的步骤动手做。画面里的界面只是示意，不是真实录屏；具体操作以本页步骤为准。

先搞懂

Claude Code 是一个在终端里运行的程序，要在某个项目文件夹里启动。它读这个文件夹里的文件，回答关于这些文件的问题，也能改文件、运行命令。

到了一个新仓库，你交给它的第一件事通常是讲解代码。对待它的回答，要像对待新同事的话一样：照着做之前，先打开它提到的文件核对一下。

在相信任何回答之前，先弄清会话的三件事：

  • 版本：不同版本的功能和默认设置不一样。
  • 模型：不同模型能做的事不一样。
  • 账号：账号决定会话一开始用哪个模型，以及你能用哪些功能。

启动时顶部会显示版本和模型；输入 /status 可以同时看到这三项。

跟着做

  1. 安装 Claude Code：

    curl -fsSL https://claude.ai/install.sh | bash

    装完后，新开一个终端窗口再继续。

  2. 检查有没有装好：

    claude --version

    打印出一个版本号，后面跟着 (Claude Code)。

    提示找不到 claude？

    说明安装目录还不在 PATH 里。先按官方的 Troubleshoot installation 修好，再继续下一步。

  3. 进入练习仓库的 project/ 文件夹，在那里启动 Claude Code。注意是 project/，不是仓库根目录。从这一步开始，这个窗口就是窗口 A：

    cd {{DIR}}/project
claude
    • 第一次启动要登录：先选账号类型，再到浏览器里完成登录。如果浏览器没有自动跳回来、而是显示一串代码，就把代码粘贴到终端里 Paste code here if prompted 那一行。
    • 接着会出现信任对话框：只信任你清楚代码来源的文件夹。一旦信任，这个仓库自带的 .claude/settings.json 就可以给 Claude 授权（比如允许它直接运行某些命令），对话框会先把这些授权列出来。别人的仓库刚克隆下来时，先别信任，退出后读一遍它的 .claude/ 文件夹。你自己的练习仓库可以放心：读完对话框，选择信任。

    输入框上方显示版本、模型和当前文件夹；输入框下方的状态栏通常显示 ⏵⏵ auto mode on，也就是自动模式，日常操作不会来问你。第 2 课会讲各种模式。

  4. /status

    Status 标签页列出版本、模型和你登录的账号（Login method、Email 等几行）。按 Esc 关闭。

    你的会话和同事的不一样时（比如同事能选某个模型，你选不了），就看这个页面，先对比账号这几行。如果你的终端里设置了 ANTHROPIC_API_KEY，你批准后 Claude Code 会改用这个 Key，而不是你的订阅；/status 会标出哪份凭据没有在用。

  5. 问一个关于代码的问题，并在中途叫停：

    what does this project do?

    意思：这个项目是做什么的？

    Claude 还在回答时，按一下 Esc。它会停下来等你的下一条指令，已经做完的部分会保留。以后发现它跑偏了，随时按 Esc，再告诉它你真正要什么。

    然后把问题再发一次，这次让它答完，接着问：

    which file parses linkcheck.json, and how do I run the tests?

    意思：哪个文件负责解析 linkcheck.json？测试怎么运行？

    回答里提到 src/config.js 和 npm test，具体措辞每次都不一样。为了回答，它会去读文件，也可能不问你就运行一条命令（比如跑测试）。

  6. 拿源码核对它的回答。用编辑器打开 src/config.js：开头几行写着它负责解析 linkcheck.json，并且列出它读取的两个字段 files 和 ignore。再打开 package.json，里面的 test 脚本就是 npm test 实际运行的命令。

    会话先不要关，“自己练”还要用。

自己练一遍

  1. 任务：团队打算把 linkcheck 放进 CI，让含有坏链接的 PR 直接失败。同事写了一份入职笔记 practice/b-1/onboarding.md，CI 的写法要以它为准，可其中有一条说法和代码对不上。你要把它找出来改正。

  2. 还在刚才那个会话里，让 Claude 逐条核对笔记。路径前加 @，就能把这个文件直接放进提示里，不用等 Claude 自己去找、去读：

    check each claim in @practice/b-1/onboarding.md against the code. For each one, say whether the code agrees, and cite the file and line.

    意思：拿代码逐条核对这份笔记，每一条都说明代码是否支持，并给出文件和行号。

  3. Claude 说哪条和代码矛盾，你就亲自打开它引用的文件和行，自己读。判断哪条说错了，要以代码为准，不能以笔记或 Claude 的话为准。它要是还指出某条说法漏掉了一些情况，不用管：只改和代码矛盾的那一条。

  4. 在编辑器里把那条改成一句话，写清楚代码实际是怎么做的，其他几条不动。如果 Claude 已经动手改了笔记，用 git diff 看它改了什么，只有和代码一致才保留。

  5. 在窗口 A 输入 /exit 结束会话，然后运行 git status，应该只列出 practice/b-1/onboarding.md。提交它，第 2 课要从干净的状态开始：

    git commit -am "Correct the onboarding notes"

检查过关

  1. npm run check -- b-1

    每一项都是 PASS。检查会在你运行它的这个终端里自己跑一次 claude --version，并读取你改过的笔记。

    出现 Could not read package.json 或 Missing script: "check"？

    说明你不在练习仓库里。先 cd {{DIR}}/project，再运行一次。

    第一项失败？

    在同一个终端里运行 claude --version。如果报错，按“跟着做”第 2 步修好，然后新开一个终端，再运行检查。

    第二项失败？

    读检查输出的提示：它会引用那条仍然不对的说法，或者告诉你改正后的说法还缺什么。打开 Claude 为这条说法引用的文件和行，照代码实际的做法写。

  2. 自查（这项检查程序测不到）：你能说出 /status 显示的模型和登录方式，而且确认这正是你想用的账号。

容易踩的坑

在自动模式下，Claude 可以不问你就改文件、运行命令。就算你只是提问，它也可能顺手运行一条命令，比如跑测试。官方文档的原话是 “Auto mode reduces permission prompts but does not guarantee safety”：自动模式减少了确认提示，但不保证安全。

这一课只让它读代码。如果它停下来问你要不要执行某个操作，先看清楚它要做什么再回答。第 2 课会教你决定哪些事它可以自己做。

第 2 课 / 共 8 课 · 初级 · 约 25 分钟

权限模式与计划模式

学完这课，你能为一项任务选合适的权限模式，判断一个改动需不需要先出计划，并且在 Claude 动你的文件之前，用计划模式只批准你愿意合并的方案。

先搞懂

权限模式决定 Claude 哪些操作可以不先问你。新会话从自动模式开始：由另一个模型（叫“分类器”）代替你审查 Claude 的操作，超出你请求范围的动作会被拦下。但工作目录里普通源码文件的修改不会送去给分类器审，自动模式直接放行。这些修改该不该出现在这次改动里，要你自己判断。

按 Shift+Tab 切换模式，输入框下方的状态栏会显示当前是哪个模式：

状态栏显示模式什么时候用
⏵⏵ auto mode onAuto 自动日常操作不再询问。适合大多数你信得过整体方向的工作
⏸ plan mode onPlan 计划Claude 先探索、写出方案；你批准之前，它不能改你的文件
⏸ manual mode onManual 手动改文件和运行大多数命令前都先问你。适合敏感工作，或者你本来就想逐步把关的时候
⏵⏵ accept edits onAccept edits在工作目录内改文件、运行 mkdir、mv、rm 这类常见文件命令，都不再询问。适合事后统一审查的代码

什么时候先出计划：思路还不确定、改动涉及好几个文件、或者你不熟悉这块代码。如果整个改动一句话就能说清（比如改一个错别字），就不必出计划。真要出计划，就只批准你愿意合并的那一份。

跟着做

  1. 在窗口 B 确认练习仓库没有未提交的改动：

    cd {{DIR}}/project
git status

    nothing to commit, working tree clean

  2. 在窗口 A 的同一个文件夹里运行 claude。状态栏通常显示 ⏵⏵ auto mode on。

  3. 这次要让 src/config.js 里的 parseConfig 拒绝空文件，并补一个测试：涉及两个文件，而且是你没读过的代码，所以先出计划。按 Shift+Tab，直到状态栏显示 ⏸ plan mode on。每按一次切到下一个模式，状态栏会显示模式名称。

  4. 提出要求：

    Make parseConfig in src/config.js reject an empty file with a clear error message, and add a test for it.

    意思：让 parseConfig 遇到空文件时报一个清楚的错误，并为此加一个测试。

  5. Claude 会读文件，也可能运行命令来摸清情况，但不会改你的文件。如果需要你先做决定，它会出一道选择题，你选一项或者自己写答案，它接着规划。最后它给出方案，并问你怎么继续：

    • 通常是 Yes, and use auto mode（自动模式不可用时显示为 Yes, auto-accept edits）
    • Yes, manually approve edits
    • 一个“继续规划、修改方案”的选项

    按 Enter 之前，先看清高亮的是哪一项：Yes, and use auto mode 会批准方案并切换到自动模式。你批准之前，会话一直停在计划模式。

  6. 像审同事的方案一样审这份计划：改哪些文件，每处改了什么。假设你希望错误信息里写明文件名，让看到报错的人知道该改哪里。现在是改主意最省事的时候，因为还一个文件都没动。用方案菜单发出下面这条修改意见，按 Enter：

    Make the error say "linkcheck.json is empty", and keep the change to src/config.js and test/config.test.js.

    意思：报错内容写成 “linkcheck.json is empty”，并且只改 src/config.js 和 test/config.test.js。

    用 Enter 发送，不要按 Shift+Tab：在这个菜单上，Shift+Tab 会直接批准方案。Claude 改完方案后会再次显示菜单。你要的修改可能不在方案开头，往下翻找一找。

  7. 让改好的方案留在屏幕上，到窗口 B 运行：

    git status

    nothing to commit, working tree clean：计划模式还没有改动任何文件。

  8. 回到窗口 A，按下箭头把高亮移到 Yes, manually approve edits，按 Enter。这一次的目的就是逐步把关，亲眼看着方案落地。等你以后对方案放心了，日常一般选 Yes, and use auto mode。

    会话切换到 Manual 模式，每次改文件、运行大多数命令之前都会问你。每个请求都读一遍再回答：

    • 方案需要的改动或命令：选 Yes。
    • 测试命令 npm test：选 Yes；不想以后再被问，也可以选 Yes, and don't ask again。后者会把一条规则存进本仓库的 .claude/settings.local.json，所以只对你清楚后果的命令这样选。
    • 做得比方案多的命令，比如 npm test && git add -A：选 No。想告诉它该怎么做，就把高亮移到 No，按 Tab，输入你的说明，再按 Enter。

    用方向键和 Enter 作答。不要选 Yes, and switch to auto mode，那会结束逐步审查；这里也不要按 Shift+Tab：在改文件的请求上，它会选中“本次会话剩下的修改都允许”的那一项。

  9. Claude 做完后，回到窗口 B 再运行一次 git status。

    列出 src/config.js 和 test/config.test.js，正是方案里写的两个文件。如果还多出别的文件，回到会话里找一找是哪次修改或哪条命令写出了它。

  10. 每处改动你都亲自审过了，直接提交，“自己练”就能从干净的状态开始：

    git commit -am "Reject an empty linkcheck.json"

自己练一遍

  1. 任务：处理同事提的一张工单，不能让任何一处你审查时会打回的改动混进去。先自己把工单读一遍：

    cat practice/b-2/ticket.md

  2. 新任务要开新对话：在窗口 A 输入 /exit，再运行 claude。然后在要求前面加上 /plan，一步完成“进入计划模式”和“开始任务”：

    /plan Work the ticket in practice/b-2/ticket.md

    确认状态栏显示 ⏸ plan mode on，Claude 问什么就答什么。

  3. 以审查者的身份读方案。每一处改动都问自己：它属于这张工单吗？我愿意合并吗？方案里要是有你不会合并的要求，就用方案菜单打回去，用自己的话写明理由。要是方案已经主动漏掉了某项要求，读一读 Claude 给的理由，再决定同不同意。一直改到你愿意批准为止。

    提示（先自己想，再展开）

    想想 linkcheck 这个工具是干什么用的。如果工单里有哪条要求会让“有坏链接也照样通过”，那就是在掩盖这个工具本该发现的问题。

  4. 最终方案留在屏幕上，到窗口 B 记录此刻 git 看到的状态，以及方案说要改的文件。路径按 git status 的写法：从仓库根目录算起，用正斜杠，每行一个。下面的 printf 那行只是示例，要换成你这份方案里的文件：

    mkdir -p .practice
git status --porcelain > .practice/b-2-before.txt
printf '%s\n' src/links.js test/links.test.js > .practice/b-2-plan.txt

  5. 批准你审过的这份方案。对一份放心的方案，日常就选 Yes, and use auto mode；之后如果 Claude Code 在执行某个操作前来问你，先看清楚再答。

  6. Claude 做完后，记录此刻的状态，看一遍改动，然后提交，新文件也要一起提交，提交说明写清楚做了什么：

    git status --porcelain > .practice/b-2-after.txt
git diff
git add -A
git commit -m "Reject unknown keys in linkcheck.json"

    提交说明按你实际做的改动来写。提交后运行 git status，应该显示 nothing to commit, working tree clean。

检查过关

  1. npm run check -- b-2

    四项全部 PASS：方案在屏幕上时记录的 b-2-before.txt 里没有改动；b-2-after.txt 列出的每个文件都在 b-2-plan.txt 里；linkcheck.json 里出现未知的键（比如 ignores）时，工具以错误码 2 退出并说出这个键；遇到坏链接时，工具仍然以错误码 1 退出并报告这条链接。

    b-2-before.txt 里列出了文件？

    要么开始“自己练”时仓库本来就不干净（漏了“跟着做”第 10 步的提交），要么你批准之前 Claude 已经写了文件。从干净的状态、在计划模式下，从“自己练”第 2 步重新开始。

    b-2-after.txt 里有文件不在 b-2-plan.txt 里？

    对比你批准的方案和 Claude 实际改的内容；方案文件里的路径要和 git status 的写法一致。

    未知键那一项失败？

    对照工单的第一条要求，看 Claude 改的内容缺了什么，然后告诉它。

    有坏链接时工具不再报错？

    说明你批准的方案把工单最后一条要求也做进去了。有坏链接也能通过的构建，掩盖的正是这个工具要发现的问题。工具能抓到那个拼写错误之后，用 "ignore": ["vendor/"] 就能跳过 vendor 下的链接。让 Claude 撤销这部分，重新保存 .practice/b-2-after.txt，再提交。

容易踩的坑

你在对话里说的限制，比如“不要推送”，会让自动模式的分类器拦下相应的操作；但对话被压缩（compact）时，这句话可能会丢。第 7 课会教你用设置文件里的规则把这类限制固定下来。

第一次改动：从需求到提交

学完这课，你能把一个改动从提出需求一直做到提交，并且审查得足够仔细，在提交之前就发现它哪里做错了。

先搞懂

提了要求就照单全收，是会话出问题最常见的原因。Anthropic 的最佳实践建议分四个阶段：探索、计划、执行、提交。自动模式不会把普通源码修改交给分类器审查，所以改得对不对，要你在两个地方把关：开工前看方案，提交前看 diff。

要求写得越准，需要纠正的次数越少。一个好的要求会写明：改哪个文件、处理哪种情况、哪些功能必须保持不变、用什么检查来验证，并且要 Claude 把检查结果的输出给你看。

  1. 探索：在计划模式下进行，Claude 只读文件，不改。
  2. 计划：方案只改你预期的文件时，才批准。
  3. 执行：在自动模式下进行，它干活时你可以继续做别的。
  4. 测试：看真实的测试输出，不看 Claude 的总结。
  5. 看 diff 并纠正：测试代码也要看，发现问题就纠正。
  6. 提交：把改动保存下来，以后想撤销也方便。

跟着做

    How does this app find links in a Markdown file? Which kinds of links would it miss?

    意思：这个程序怎么在 Markdown 文件里找链接？哪些链接会被漏掉？

    回答会指向 src/links.js，并提到带标题的链接（措辞每次不同）。

  3. 计划：

    Plan a change so links with a title, in double or single quotes, are checked too, like [setup](setup.md "Setup guide") and [faq](faq.md 'FAQ'). Add a test for each to test/links.test.js, run the tests and show me the output.

    意思：规划一个改动，让带标题的链接（双引号或单引号）也被检查；两种各加一个测试到 test/links.test.js，运行测试并把输出给我看。

    读完方案再选。它应该只改 src/links.js 和 test/links.test.js；只是读一读、或者说明不用改的文件没关系。如果它还要改别的文件（比如 src/cli.js），或者要新建文件，就用方案菜单打回去，要求只改这两个文件。

    /btw in one sentence, why does the current pattern skip a link with a title?

    这个问答不会进入对话记录，所以不会影响 Claude 接下来怎么做。想改变它的做法，就正常发一条消息。

    run the tests

    太长的命令输出会被折叠成一句摘要。按 Ctrl+O 打开完整记录，在靠近末尾的地方找到测试汇总，再按一次 Ctrl+O 返回。

    每一行都要读，测试也不例外。读的时候问自己：测试覆盖了单引号和双引号两种情况吗？代码有没有把标题排除在链接地址之外？

    想在窗口 B 里看改动？

    改完再看一次 diff。如果审查没发现要改的地方，直接往下走，“自己练”里有东西等你去发现。

    commit this with a message that says what changed

    如果 Claude 把提交放在了一个新分支上也没关系，检查在哪个分支上都能过。想留在当前分支，就在要求里说明。

    在窗口 B 运行 git status，最后一行是 nothing to commit, working tree clean。

用 CLAUDE.md 写项目记忆

学完这课，你能写一份简短、内容属实的项目 CLAUDE.md，证明新会话会遵守它，并且判断每条说明应该写进哪个记忆文件。

先搞懂

每个会话都从空白的上下文开始。你的说明文件会在每次会话开始时加载，写在哪个文件里，决定了谁能看到：

位置放什么谁能看到
./CLAUDE.md命令、约定、项目结构整个团队：要提交进仓库
~/.claude/CLAUDE.md你在所有项目里都适用的习惯只有你
./CLAUDE.local.md你在这个项目里的个人笔记只有你：要加进 .gitignore
自动记忆（auto memory）Claude 自己记下的笔记，比如你让它记住的事只有你，只在这台电脑上
  • /init 会根据代码写出第一版 CLAUDE.md。写完要删减：每一行都问一句，“删掉它，Claude 会不会犯错？”
  • Claude 第二次犯同样的错，或者你第二次打同样的纠正，就该加一行了。
  • 对 Claude 说 “add this to CLAUDE.md”，它会把说明写进这个文件；说 “remember”，它会存进自动记忆。
  • 这些文件只是参考信息，Claude 不一定照办。绝对不能违反的规则要用钩子（hook）来强制，中级课程会讲。

本页把官方初级第 4 课“让会话不跑偏”放到了以后再学。这一课只要求先学完第 3 课。

跟着做

  1. 在练习仓库的 project/ 文件夹里启动 claude，然后运行：

    /init

    Claude 会读代码，把找到的命令和约定写进 CLAUDE.md。写完后，在窗口 B 用 cat CLAUDE.md 读一遍。

  2. 像要给团队看那样改一遍。用编辑器打开 CLAUDE.md，或者在窗口 A 输入 /memory，选项目里的 ./CLAUDE.md。

    • 删掉 Claude 自己读代码就能知道的内容，比如逐个文件的介绍。
    • 删掉所有只跟课程有关、跟 linkcheck 本身无关的行：凡是提到 checks/、learn/、capstone/、.github/、.devcontainer/ 的内容，凡是 npm run check、npm run learn、npm run test:checks 的行，还有“不要在 main 上工作”这类规则（那是给模板仓库用的）。
    • 剩下的每条命令，都和 package.json 里的 scripts 对照一遍。npm test 要保留，结业项目会检查它。

  3. 加一条从文件内容上就能看出有没有被遵守的约定。放在 ## Conventions 标题下；如果 /init 没写这个标题，就在文件末尾加上：

    ## Conventions

- Every new JavaScript file in `src/` starts with the line `// SPDX-License-Identifier: MIT`.

    意思：src/ 下每个新建的 JavaScript 文件，第一行都写 // SPDX-License-Identifier: MIT。

    许可证头是很常见的项目规则，而 linkcheck 现在还没有一个文件带它，所以能清楚看出会话有没有遵守。规则里写明了适用于哪些文件：要是在 shell 脚本或 JSON 文件开头加一行 //，文件就坏了，而每个会话都会读到这条规则。

  4. 保存 CLAUDE.md，然后在窗口 B 提交：

    git add CLAUDE.md
git commit -m "Add project instructions for Claude Code"

  5. 输入 /exit，再运行 claude 开一个新会话，让它加载带新规则的 CLAUDE.md。然后：

    /context all

    Memory files 下面列出了 CLAUDE.md，说明会话已经加载它了。只输入 /context 时这个列表可能是折叠的，加上 all 会展开。

  6. 要求一个会新建文件的改动，要求里不提许可证头：

    Add src/stats.js with a function countLinks(markdown) that returns how many links findLinks finds. Add a test in test/stats.test.js, run the tests and commit.

    意思：新建 src/stats.js，写一个 countLinks 函数，返回 findLinks 找到的链接数；在 test/stats.test.js 里加测试，跑测试并提交。

  7. head -1 src/stats.js
git status

    第一行是 // SPDX-License-Identifier: MIT，虽然这次会话里你从没提过；git status 显示 nothing to commit, working tree clean。

    git status 列出了 src/stats.js？

    说明 Claude 还没提交，让它提交。

自己练一遍

    意思：1. 命令行错误输出到 stderr，并以 linkcheck: 开头。2. 提交前用 npm run tests 跑测试。3. 我的样例文档放在 ~/scratch/linkcheck-docs，我要冒烟测试时就在上面跑命令行。4. 回复要简短，结尾不要总结，所有项目都这样。

  2. 动手之前先逐条决定去处：项目的 CLAUDE.md、CLAUDE.local.md、你的用户文件，还是哪里都不写。凡是要写进会提交的文件的，必须属实：拿它和 package.json、src/cli.js 对照，因为以后每个会话、每位同事都会读到它。

    对答案（先自己判断，再展开）

    Add this to CLAUDE.md: CLI errors go to stderr and start with `linkcheck:`.

  5. 你希望在所有项目里都生效的习惯，写进你的用户文件 ~/.claude/CLAUDE.md（/memory 里也能找到它）。这个文件会影响你以后在任何项目里开的每一个会话，所以写不写由你决定。

  6. 提交 CLAUDE.md 和 .gitignore：

    git add CLAUDE.md .gitignore
git commit -m "Sort project notes into the right memory files"

    git status 显示干净，因为 git 已经忽略了 CLAUDE.local.md。

把重复工作做成技能

学完这课，你能把一套反复使用的工作流程做成项目技能，决定哪些请求会自动加载它，并且审查它做出来的改动。

先搞懂

同一套操作说明，你第三次往对话里粘贴的时候，就该把它写成技能（skill）了。技能是一个文件夹，里面放一个 SKILL.md：开头一段 YAML 说明（frontmatter），写明这个技能是做什么的；后面是 Claude 要照着执行的步骤。项目技能放在 .claude/skills/<名字>/SKILL.md，提交进仓库后，团队里每个人都能用。

Claude 决定要不要加载某个技能，看的是技能列表里的简介（description），以及 when_to_use 字段（如果写了），不看技能正文。技能有两种触发方式，触发后 Claude Code 都会加载完整的说明：

  • 你输入 /技能名，后面跟一段内容，这段内容会填进正文里的 $ARGUMENTS。
  • 你的请求和技能简介对得上，Claude 就自己加载。

每个能被自动加载的技能都会出现在技能列表里，每一轮对话都要占用一点上下文。frontmatter 里写上 disable-model-invocation: true，技能就只能靠输入名字来触发，简介也不再进入上下文。有副作用、或者执行时机必须由你掌控的流程（比如提交、部署）适合这样设置。

联系你的工作：询盘分级、客户背调，都可以做成这样一个技能。

跟着做

  1. 本课直接在练习仓库里练（原课也允许这样做）。下载教程自带的示例技能 five-whys，它会连着追问五个“为什么”，找出问题的根本原因。用之前先读一遍：

    cd {{DIR}}/project
mkdir -p .claude/skills/five-whys
curl -fsSL https://raw.githubusercontent.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/main/examples/intermediate/01-first-skill/dot-claude/skills/five-whys/SKILL.md -o .claude/skills/five-whys/SKILL.md
cat .claude/skills/five-whys/SKILL.md

    去掉开头的注释后，文件是这样开始的：

    ---
name: five-whys
description: Finds the root cause of a bug, failure or recurring problem by asking "why" until the answer is a cause you can fix. Use when the user asks why something keeps happening, or wants the root cause rather than a quick fix.
argument-hint: "[problem]"
---

Find the root cause of this problem: $ARGUMENTS

    后面是排查步骤，以及一条规则 “Don't change any files.”（不要改任何文件）。

  2. 启动 claude，查看技能列表：

    /skills

    列表里有 five-whys。它放在 .claude/skills/ 下，所以是项目技能。

    列表里没有？

    如果会话启动时 .claude/skills/ 文件夹还不存在，要先运行 /reload-skills；以后每次改动这个文件夹，也要再运行一次。

  3. 触发方式一：输入名字运行：

    /five-whys npm run linkcheck -- samples exits with code 1

    意思：用 five-whys 分析 “npm run linkcheck -- samples 以错误码 1 退出” 这个问题。

    读它给出的因果链、根本原因和修复建议，措辞每次不同。然后在窗口 B 运行 git status --short。

    新增的只有你下载的技能文件。这个技能要求 Claude 不改任何东西；要是出现了代码改动，先查清楚是怎么回事再继续。

整理项目记忆，查看加载了什么

学完这课，你能把项目说明拆成导入文件和分范围规则；Claude 不遵守某条说明时，能查出是哪些说明文件加载了、哪些没有。

先搞懂

CLAUDE.md 太长不好维护，而且每一行都会加载进每个会话。有两种办法把它拆开：

  • 导入（import）：在 CLAUDE.md 里写一行 @docs/conventions.md 这样的内容，被引用的文件会跟着一起加载。这只是让文件更有条理，并不节省上下文。
  • 规则（rule）：.claude/rules/ 下的 Markdown 文件。frontmatter 里写了 paths: 的规则，只有 Claude 处理匹配的文件时才加载。
说明文件什么时候加载
项目根目录的 CLAUDE.md，以及没写 paths: 的规则会话开始时
被 @路径 导入的文件和导入它的文件一起加载
写了 paths: 的规则Claude 读、写或编辑匹配的文件时，包括用 cat、head 这类单文件 shell 命令查看

Claude 不遵守某条说明时，先查这份文件有没有加载。如果加载了，问题多半出在写法上：写得更具体，并删掉和它矛盾的说明。

paths:
  - "test/**/*.js"
---

# Testing

    意思：只对 test/ 下的 .js 文件生效；只能用 node:test 和 node:assert/strict 写测试，不用其他测试库。

权限、设置范围与沙箱

学完这课，你能挑出范围窄的权限规则，放进合适的设置文件，并且亲手验证沙箱的边界。

先搞懂

规则写在哪个设置文件里，决定了它对谁生效：

文件对谁生效放什么
~/.claude/settings.json你自己，所有项目个人默认设置
.claude/settings.json（提交进仓库）项目里的所有人团队规则
.claude/settings.local.json（不进 git）你自己，只限这个项目个人选择
Managed settings（托管设置）你所在的组织组织政策

同一个设置项写在多处时，级别高的生效，从高到低是：托管设置、命令行参数、本地文件、共享的项目文件、用户文件。permissions.allow 这类规则列表则会把各个文件里的合并起来。规则之间的判断顺序是先 deny（拒绝），再 ask（询问），最后 allow（允许），第一条匹配上的说了算。

在自动模式下，一个操作只要匹配到你的某条规则，就会在分类器之前按规则处理（少数例外，比如写入受保护的路径）：deny 直接拦下，ask 来问你，allow 直接放行。自动模式会忽略范围太宽的 allow 规则（比如允许运行任意包管理器命令的规则），保留 Bash(npm test) 这样范围窄的。

沙箱默认只允许 shell 命令写入项目目录、你用户的临时目录和你额外加入的目录，这道边界由操作系统来强制执行。

联系你的工作：接真实客户资料之前，先用这一课的方法把 Claude 能读什么、能写到哪里限定好。

跟着做

  1. 在练习仓库里，用 Manual 模式启动会话：

    cd {{DIR}}/project
claude --permission-mode default

    确认状态栏显示 manual mode on。这里特意用 Manual 模式：自动模式可能不弹提示就放行测试命令，那样“没有弹提示”就证明不了是 allow 规则在起作用。

    然后运行 /status，Setting sources 那一行列出了这次会话加载的设置文件。再打开 /sandbox 看一眼：比较规则时先让沙箱保持关闭，看完关掉这个面板。

  2. 把团队规则写进 .claude/settings.json。如果这个文件里已经有别的设置，把下面这段合并进去，不要整个覆盖。这几条规则包括：官方文档推荐的、禁止 Claude 读取 .env 文件的规则（这类文件里通常放账号密码），允许直接运行一条具体的测试命令，以及推送前必须先问你：

    {
  "permissions": {
    "allow": ["Bash(npm test)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}

    光靠自动模式，Claude 是能读 .env 的，挡住它的是这两条 deny 规则。ask 规则则让 Claude Code 在推送前一定来问你，自动模式下也一样。规则文件一改动，Claude Code 就会重新加载。

  3. /permissions

    列出每一条规则，以及它来自哪个设置文件。

  4. 练习仓库里没有 .env，在窗口 B 建一个装着假数据的：

    echo "DEMO_TOKEN=not-a-real-secret" > .env

    回到窗口 A，让 Claude 去读它：

    Read .env and tell me what it holds.

    deny 规则拦下了这次读取。

    然后在窗口 B 删掉这个假文件：rm .env

  5. Run npm test

    读测试结果。在 Manual 模式下、沙箱关着、又没有匹配的 ask 或 deny 规则时，这条命令能不弹提示直接运行，因为 allow 规则覆盖了它。

    还是弹了提示？

    先检查命令本身和规则来源，不要为了省事去批准一条范围更宽的授权。

容易踩的坑

沙箱只管 shell 命令。Claude 的文件工具和网页工具受权限规则约束；钩子和本地 MCP 服务器在沙箱外运行，拥有你的全部权限。另外，沙箱启动失败时，Claude Code 会在没有沙箱的情况下照常运行命令，除非你把 sandbox.failIfUnavailable 设为 true。

Read 的 deny 规则拦不住一个自己去打开文件的脚本。开启沙箱后，Claude Code 会把这些 deny 路径同时加进沙箱的禁读列表。

用 MCP 连接外部工具

学完这课，你能按合适的范围接入一个锁定了版本的 MCP 服务器，并借助它拿到的浏览器信息，找出并修好网页上的一个错误。

先搞懂

MCP（Model Context Protocol，模型上下文协议）让 Claude Code 能使用另一个程序提供的工具，这个程序叫 MCP 服务器。本课用 Google 出的 Chrome DevTools MCP：查看本地网页的控制台、诊断里面的错误，并截图留下修好后的样子。

范围谁能用存在哪里
Local（默认）你自己，只限这个项目~/.claude.json
Project项目里的所有人项目根目录的 .mcp.json，提交进仓库
User你自己，所有项目~/.claude.json
  • 在交互式会话里，项目里的服务器要你批准后才会被使用。批准一个服务器，和批准它的某一次工具调用，是两件分开的事。
  • 共享的 .mcp.json 里永远不要写令牌（token）：写成 ${VAR}，让每位同事自己设置这个环境变量。
  • 默认开启工具搜索，会话开始时只加载工具名称和服务器说明。

数据外流提醒：Chrome DevTools MCP 默认会向 Google 发送使用统计，可能把性能追踪的网址发给 Google 的 CrUX 接口，还会联网检查 npm 更新。本课每次运行都把这三项关掉。即使这样，Claude 打开的网页仍然是从网上加载的，而且这个服务器能让 Claude 看到那个浏览器里的一切。这个隔离浏览器只用来跑本地演示，不要登录个人账号，也不要打开敏感页面。

需要先装好 Chrome，以及 Node.js 自带的 npm。

跟着做

  1. 把下面这个网页存成 .practice/demo.html。里面埋了一个浏览器端的错误，先别修：

    cd {{DIR}}/project
cat > .practice/demo.html <<'EOF'
<!doctype html>
<title>Linkcheck demo</title>
<a href="#guide">Guide</a> <a href="#reference">Reference</a>
<p id="link-count">Counting links...</p>
<script>
const links = document.querySelectorAll('a');
document.querySelector('#link-total').textContent = `${links.length} links ready`;
</script>
EOF

  2. 在本地范围给自己接入这个服务器。版本固定为 1.10.1；--isolated 让浏览器使用一个临时的配置；另外两个参数和那个环境变量负责关掉三项数据外流。-- 后面的部分是服务器自己的启动命令：

    claude mcp add --env CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS=1 --transport stdio chrome-devtools -- npx -y chrome-devtools-mcp@1.10.1 --isolated --no-usage-statistics --no-performance-crux
  3. claude mcp get chrome-devtools

    显示这个服务器在哪个范围（这里是 local），以及它的状态。

  4. 第一次使用 MCP 工具，用 Manual 模式启动：

    claude --permission-mode default

    运行 /mcp，选中 chrome-devtools，查看它的状态和工具。列表里只显示工具数量，选中服务器后才能看到工具清单。然后提问：

    Use the chrome-devtools tools to open .practice/demo.html as a file: URL. Read the title, visible count and console error. Report the error and its source location, without editing any files.

    意思：用 chrome-devtools 工具以 file: 地址打开这个网页，读出标题、页面上显示的数量和控制台报错；报告错误和出错位置，不要改任何文件。

    Claude Code 每次询问工具调用时，都看清工具名称和输入，只批准这一次，这个练习里不要给长期授权。

    读实际的工具输出：页面上一直显示 Counting links...，脚本在更新一个找不到的元素时出错了。不同浏览器的报错措辞可能不一样。

    审完第一次调用后，按 Shift+Tab 切到 ⏵⏵ auto mode on（如果可用），后面的调用就交给自动模式的检查。

自己练一遍

  1. 任务：让每位同事都用上你审查过的这个浏览器服务器，然后用它修好那个坏掉的演示网页。先删掉本地范围的那份配置，否则它会优先于同名的项目服务器：

    claude mcp remove chrome-devtools -s local

    如果提示找不到本地服务器，确认你在添加它的那个仓库里：本地范围只属于那个项目。

  2. 用项目范围重新添加同一个服务器。这条命令会在仓库根目录写出 .mcp.json，和里面已有的服务器放在一起：

    claude mcp add --scope project --env CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS=1 --transport stdio chrome-devtools -- npx -y chrome-devtools-mcp@1.10.1 --isolated --no-usage-statistics --no-performance-crux

  3. 提交之前先读一遍 .mcp.json：版本号锁定了没有，两个参数和那个环境变量在不在，里面有没有令牌。确认没问题再提交：

    cat .mcp.json
git add .mcp.json
git commit -m "Share the reviewed chrome-devtools MCP server"

  4. 退出“跟着做”的会话，重新运行 claude。它会问你是否使用项目里新加的服务器。只有审查过 .mcp.json 里这个服务器的命令和参数，才批准，因为这些内容决定了你电脑上会运行什么代码；如果 .mcp.json 里有你没审查过的服务器，拒绝并查清楚。然后运行 /mcp，选中这个服务器，确认已经连上。修网页这一步保持自动模式。

  5. 用项目里的浏览器工具重新加载 .practice/demo.html，改代码之前先读控制台。判断问题出在查找元素，还是计算数量：把报错指向的那一行，和页面里已有的结果元素对比一下。要修的是对不上的那个查找，计算部分保持不变；把异常吞掉，页面照样是坏的。

    提示（先自己看，再展开）

    对比脚本里 querySelector 要找的 id，和页面上 <p> 元素实际的 id。

    让 Claude 只做这一处修复，然后用 MCP 工具重新加载页面，确认显示的数量和控制台都正常。

    页面显示 2 links ready，控制台没有脚本错误。

    最后让服务器把修好的页面截图，存成 .practice/i-7-page.png：

    Use the chrome-devtools tools to save a PNG screenshot of the repaired page to .practice/i-7-page.png

检查过关

  1. git show HEAD:.mcp.json | jq '.mcpServers["chrome-devtools"]'
npm run check -- i-7

    全部 PASS：已提交的 .mcp.json 锁定了具体版本，并关掉了使用统计、CrUX 查询和更新检查；.practice/i-7-page.png 是修复之后截的图；演示脚本显示 2 links ready，没有脚本错误（直接把数量写死过不了检查）。

    服务器那一项失败？

    把每个参数和“跟着做”里的命令逐一对比。写成 @latest 不算锁定版本。

    截图缺失，或者比修复还早？

    确认服务器已经连上，再让它重新存一次 PNG。

    演示网页那一项失败？

    回看“自己练”第 5 步：删掉脚本或者吞掉报错，都不算修好了数量显示。

  2. 自查：你审过第一次 MCP 工具调用；你是用项目里的服务器读到真实的控制台报错的；修好后重新加载，确认了数量正确、控制台干净。

容易踩的坑

用 claude -p 写脚本运行时，Claude Code 会不经询问就加载项目里的 MCP 服务器。所以在任何仓库里写脚本调用 Claude Code 之前，先读一遍它的 .mcp.json。另外，自动模式下某次工具调用没弹提示，并不代表你给过长期授权。

想重新被问一次要不要用项目里的服务器，运行 claude mcp reset-project-choices，然后重启 Claude Code。错过了批准提示的话，在 /mcp 里也能批准。

第三方 MCP 服务器能在你的电脑上运行代码，或者给 Claude 加上新工具。安装之前先审查；原教程不负责审核它们。
