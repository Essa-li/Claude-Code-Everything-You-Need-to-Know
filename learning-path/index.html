每课都按同一个流程走：先搞懂一个概念，跟着示例逐步操作，自己再练一遍，跑检查命令确认通过，最后做 3–4 道过关小测。小测通过后，地图上会亮起下一课。

开始第 1 课

开始前：开好两个终端窗口

每一步开头都有一个标签，告诉你这一步在哪个窗口操作：

窗口 A · Claude Code运行 claude 后的会话。在这里输入 /status 这类斜杠命令，以及要发给 Claude 的话。
窗口 B · 普通终端在练习仓库文件夹里运行 git、npm、cat 等命令。
编辑器用来修改文件，例如 TextEdit、VS Code。
只看不用输入，看清楚屏幕上出现了什么。

本页按 Mac 编写。中级课程要求 Mac、Linux 或 WSL 2；如果用 Windows，请对照英文原课。

准备清单

  1. 付费 Claude 套餐（Pro、Max、Team 或 Enterprise）或 Claude Console 账号。免费版不含 Claude Code。
  2. Mac 上装好 git 和 Node.js LTS。终端里运行 git --version 和 node --version 都能打印出版本号即可。
  3. 打开 claude-code-practice，点 Use this template → Create a new repository，建好你自己的练习仓库，再克隆到电脑上。所有练习都在这个仓库里做，不会碰到你的真实资料。
  4. 在下面填写练习仓库在电脑上的路径。之后每课的命令会自动换成这个路径。

掌握路径

练习仓库里另有一个官方英文带练程序（在窗口 B 运行 npm run learn），内容和本页一致，可以对照使用。你的进度只保存在这台设备的浏览器里。

第 1 课 / 共 8 课 · 初级 · 约 20 分钟

安装、登录、熟悉界面

学完这课，你能装好 Claude Code 并登录，在仓库里启动它，并且说得出当前会话用的是哪个版本、哪个模型、哪个账号。

先搞懂

Claude Code 是一个在终端里运行的程序，要在某个项目文件夹里启动。它会读这个文件夹里的文件来回答问题，后面几课还会修改这些文件。

在相信它给的答案之前，先确认三件事：

  • 版本：不同版本的功能和默认设置不一样。
  • 模型：不同模型的能力不一样。
  • 账号：账号决定你能用哪些功能和模型。

启动时顶部会显示版本和模型；输入 /status 能把三项一起看到。

跟着做

  1. 安装 Claude Code：

    curl -fsSL https://claude.ai/install.sh | bash

    安装完成后，关掉这个终端，新开一个终端窗口。

  2. 检查是否装好：

    claude --version

    一个版本号，后面跟着 (Claude Code)。

    提示找不到 claude？

    说明安装目录还没加入 PATH。按官方 Troubleshoot installation 处理好再继续。

  3. 进入练习仓库，把版本号保存下来，后面检查要用：

    cd {{DIR}}
mkdir -p .practice
claude --version > .practice/version.txt

    路径中间有空格的话，要用引号括起来。

  4. 在同一个文件夹里启动 Claude Code。从这一步起，这个窗口就是窗口 A：

    claude
    • 第一次会要求登录：先选账号类型，再到浏览器里完成登录。如果浏览器显示一串代码、没有自动跳回终端，就把代码粘贴到终端的 Paste code here if prompted 提示处。
    • 会弹出信任对话框：默认高亮的是 No, exit，直接回车会退出。按下箭头选 Yes, I trust this folder 再回车。这个仓库是你自己建的，可以信任。

    输入框上方的顶部区域，显示版本、模型和当前文件夹。

  5. 查看会话状态：

    /status

    Status 标签页列出版本、模型和账号（Login method、Email 等行）。按 Esc 关闭。

    你的版本可能比本教程核对时用的新：教程按 stable 发布通道核对，而 Claude Code 默认跟随 latest 通道。

  6. 就代码问它两个问题。可以直接复制英文，也可以改用中文问：

    what does this project do?
    which file parses linkcheck.json, and how do I run the tests?

    意思：这个项目是做什么的？哪个文件解析 linkcheck.json？怎么运行测试？

    回答里提到 src/config.js 和 npm test。具体措辞每次都不一样。

  7. 结束会话：

    /exit

自己练一遍

  1. 还在练习仓库里，再保存一次版本号：claude --version > .practice/version.txt

  2. 运行 claude 启动会话。

  3. 打开 /status，记下模型和账号。

  4. 用自己的话问两个关于代码的问题，然后输入 /exit 结束。

检查过关

  1. 确认版本号已保存：

    cat .practice/version.txt

    类似 X.Y.Z (Claude Code) 的一行。

  2. 运行本课检查：

    npm run check -- b-1

    每一项都显示 PASS。

    出现 Could not read package.json 或 Missing script: "check"？

    说明你不在练习仓库里。先 cd {{DIR}}，再运行一次。

    如果是第一项失败：单独运行 claude --version。它报错就回到第 2 步处理；它能打印版本，就在练习仓库里重新保存一次。

  3. 自查（检查程序不测这一项）：你能说出 /status 显示的是哪个模型、哪个账号。

容易踩的坑

新会话默认可以不先问你，就修改大多数文件、运行大多数命令。这一课只提问就好，下一课会教你怎么控制它能做什么。

即使只是提问，Claude 也可能为了回答你去运行会写文件的命令（比如跑一遍测试）。所以会话结束后，在窗口 B 运行 git status：如果列出了文件，先提交或删掉，再开始第 2 课。

第 2 课 / 共 8 课 · 初级 · 约 20 分钟

权限模式与计划模式

学完这课，你能为一个任务选合适的权限模式，在会话中途切换模式，并用计划模式先批准方案，再让 Claude 动你的文件。

先搞懂

权限模式决定 Claude 哪些操作可以不先问你。按 Shift+Tab 切换模式，输入框下方的状态栏始终显示当前是哪个模式。现在需要掌握四种：

状态栏显示模式不问你就能做的事
⏸ manual mode onManual 手动只能读
⏵⏵ accept edits onAccept edits读、改文件、运行常见的文件命令
⏸ plan mode onPlan 计划读，再写出方案；你批准之前不能改文件
⏵⏵ auto mode onAuto 自动全部都能做，后台有安全检查

敏感工作、不熟悉的代码用 Manual，每个动作你都亲自过目；长任务用 Auto，省得每一步都要批准。

最先要养成的习惯是用计划模式：Claude 改任何文件之前，你先看到完整方案。

跟着做

  1. 开始前，确认练习仓库没有未提交的改动：

    cd {{DIR}}
git status

    nothing to commit, working tree clean

  2. 运行 claude，看一下状态栏。新会话通常是自动模式。

  3. 反复按 Shift+Tab，直到状态栏显示 ⏸ plan mode on。从自动模式开始，依次会切到 Manual、Accept edits、Plan。

  4. 提出改动要求：

    Make parseConfig in src/config.js reject an empty file with a clear error message, and add a test for it.

    意思：让 src/config.js 里的 parseConfig 遇到空文件时报一个清楚的错误，并为此加一个测试。

  5. Claude 会读文件，也可能运行命令来了解情况，但不会改你的文件。如果需要你先做决定，它会出一道选择题，选一项或自己输入回答即可。之后它给出方案，并提供三个选项：

    • Yes, and use auto mode（自动模式不可用时显示为 Yes, auto-accept edits）
    • Yes, manually approve edits
    • 一个输入框：Tell Claude what to change

    菜单打开时默认高亮第一项。你选择之前，会话一直停在计划模式。

  6. 先把方案退回一次，就算它看起来没问题也退回，这是为了练习。按下箭头移到 Tell Claude what to change，在那一行输入下面这句修改意见，按 Enter：

    Keep the change to src/config.js and test/config.test.js. Don't add new files.

    意思：只改 src/config.js 和 test/config.test.js，不要新建文件。

    一定要用 Enter 发送，不能按 Shift+Tab：在这个菜单上，Shift+Tab 会直接批准方案。

    还没输入就按了 Enter？

    屏幕会显示 User rejected Claude's plan:，会话仍在计划模式等你。在输入框里补上修改意见就行。

  7. 修改后的方案没问题时，先别批准，让它留在屏幕上。在窗口 B 记录此刻 git 看到的状态，以及方案说要改的文件：

    git status --porcelain > .practice/b-2-before.txt
printf '%s\n' src/config.js test/config.test.js > .practice/b-2-plan.txt

  8. 回到窗口 A，按下箭头移到 Yes, manually approve edits，按 Enter。注意不要在默认高亮的第一项上直接回车，那样 Claude 改文件就不会再问你了。

    会话切到 Manual 模式，每次改文件、跑大多数命令前都会问你。每个请求都读一遍，回答最简单的 Yes。其他几个 Yes 选项会让它以后不再问这一类操作，或者把会话切到别的模式。如果某条命令超出了方案范围，就选 No，告诉它该怎么做。

  9. Claude 做完后，在窗口 B 再记录一次：

    git status --porcelain > .practice/b-2-after.txt

  10. 把示例的改动先存到一边，让“自己练”从干净状态开始。git 会忽略 .practice/，所以记录文件会保留：

    git stash push --include-untracked -m b-2-example

自己练一遍

  1. 按 Shift+Tab 切到 ⏸ plan mode on。

  2. 提一个你自己想要的小改动，回答 Claude 提出的问题。

  3. 在 Tell Claude what to change 里写一条修改意见，按 Enter，把方案退回一次。

  4. 最终方案留在屏幕上时，在窗口 B 运行跟着做第 7 步的两条命令，把 printf 那行换成你这个方案要改的文件，一行一个路径。

  5. 选 Yes, manually approve edits，逐个读请求再批准。做完后在窗口 B 运行 git status --porcelain > .practice/b-2-after.txt。

  6. 到这里停下，不要提交。下一课要从干净的状态开始，把一个新改动做到提交为止。

检查过关

  1. 运行本课检查：

    npm run check -- b-2

    全部 PASS：b-2-before.txt 是空的，b-2-after.txt 里的每个路径都出现在 b-2-plan.txt 里。

    b-2-before.txt 里列出了文件？

    有两种可能：开始时仓库本来就不干净（比如漏了跟着做的第 10 步），或者你批准之前 Claude 已经写了文件（检查一下发送要求时状态栏是不是 ⏸ plan mode on）。

    处理方法：运行 git stash push --include-untracked，再从“自己练”第 1 步重做一遍。

    某个改过的路径不在 b-2-plan.txt 里？

    确认路径的写法和 git status 显示的一样（从仓库根目录算起，用正斜杠）。然后对比你批准的方案和 Claude 实际改了什么。

  2. 自查：用一句话说出，什么时候你会选 Manual 而不是 Auto。

第 3 课 / 共 8 课 · 初级 · 约 20 分钟

第一次改动：从需求到提交

学完这课，你能把一个改动从提出到提交完整走一遍：探索、计划、执行、测试、看改动、纠正、提交。

先搞懂

提了要求就照单全收，是会话出问题最常见的原因。Anthropic 的最佳实践建议分四个阶段：探索、计划、执行、提交。本课在每一步都加了一道检查：

  1. 探索：在计划模式里进行，Claude 只读、只回答，不改任何东西。
  2. 计划：方案符合你的要求再批准。
  3. 执行：改动一个个批准。
  4. 测试：能证明改动有效的是测试结果，不是 Claude 写的总结。
  5. 看改动：逐行读 diff。
  6. 纠正：不想要的地方，直接用大白话告诉它。
  7. 提交：保存改动，以后想撤销也容易。

示例任务：练习项目会检查 Markdown 里的链接，但会漏掉带标题的链接，比如 [setup](setup.md "Setup guide")。你要修好它。

跟着做

  1. 确认仓库干净。第 2 课的改动如果还在，先存到一边：

    cd {{DIR}}
git stash push --include-untracked -m b-2
git status

    nothing to commit, working tree clean

  2. 探索。启动 claude，按 Shift+Tab 切到 ⏸ plan mode on，然后问：

    How does this app find links in a Markdown file? Which kinds of links would it miss?

    意思：这个程序怎么在 Markdown 文件里找链接？哪些链接会被漏掉？

    提到 src/links.js，并说到带标题的链接会被漏掉。

  3. 计划：

    Plan a change so links with a title, like [setup](setup.md "Setup guide"), are checked too. Add a test for it to test/links.test.js.

    意思：规划一个改动，让带标题的链接也被检查到，并在 test/links.test.js 里加测试。

    读方案。只涉及 src/links.js 和 test/links.test.js 时，选 Yes, manually approve edits。如果还涉及别的文件，像第 2 课那样在 Tell Claude what to change 里退回，要求只改这两个文件。

  4. 执行和测试。逐个批准改动。运行测试等命令前它也会问你：命令确实是方案需要的就答 Yes；如果命令超出范围（比如要 stash、覆盖或移动文件），就答 No 并说明该怎么做。不要选 Yes, and switch to auto mode，否则本课剩下的步骤就改由后台安全检查替你审，而不是你自己审。

    就算 Claude 已经跑过测试，也再要求一次，亲眼看结果：

    run the tests

    输出太长会被折叠，按 Ctrl+O 展开，找到最后的测试汇总，再按 Esc 返回。

    测试汇总显示 fail 0。

  5. 看改动。输入 /diff，会出现下面两种界面之一：

    • 对话旁边的面板：列表默认不显示测试文件，要点一下统计测试文件的那一行（比如 1 test/generated (show)）。如果面板已经自动打开，就直接在里面看，因为再输入 /diff 会把它关掉。
    • 输入框上方的列表：用方向键选文件，Enter 查看，Esc 返回。

    每一行都要读，测试也要读。

    想在窗口 B 里看改动？

    运行 git diff。Claude 新建的文件要先运行 git add -N 文件名 才会出现在 diff 里。屏幕停在 : 提示符时，按 q 退出。

  6. 纠正。读新加的测试。如果它只测了双引号的标题，就要求：

    The test covers only double-quoted titles. Add a case for a single-quoted title, like [faq](faq.md 'FAQ'), and run the tests again.

    意思：测试只覆盖了双引号标题，再加一个单引号标题的用例，然后重新跑测试。

    如果它已经测了单引号，就换一个你想要的小改动，比如把每种标题拆成单独的测试。改完再看一次 diff。

  7. 提交：

    commit this with a message that says what changed

    意思：提交这些改动，提交说明写清楚改了什么。

    运行 commit 前它会问你。把整条命令读完再选 Yes。它如果顺便建了一个分支也没关系，检查在哪个分支上都能通过。

  8. 记下这次提交，并确认没有遗留：

    git rev-parse HEAD > .practice/b-3-commit.txt
git status

    nothing to commit, working tree clean

自己练一遍

  1. 任务：修第二个漏洞。目标地址写在尖括号里的链接，比如 [my notes](<my notes.md>)，目前也会被漏掉。

  2. 在计划模式里探索：问它这个程序怎么读取链接的目标地址。

  3. 规划改动，要求在 test/links.test.js 里加测试。方案涉及别的文件就退回，没问题再选 Yes, manually approve edits。

  4. 批准改动和测试命令，然后让 Claude 跑测试。

  5. 用 /diff 把整个改动看一遍，测试文件也要看。

  6. 提一个纠正要求，再小也可以，然后再看一次 diff。

  7. 纠正完成后，让 Claude 把改动、测试和你的纠正一起提交。

  8. 运行 git rev-parse HEAD > .practice/b-3-commit.txt

检查过关

  1. npm test
git status --porcelain
npm run check -- b-3

    npm test 显示 fail 0，git status --porcelain 没有任何输出，检查全部 PASS。

    提交里没有测试文件，或者只有测试文件？

    说明代码和测试没有放进同一次提交。如果还没推送，可以让 Claude 用 git commit --amend 补上缺的部分，或者把最后两次提交合并成一次，然后重新保存 git rev-parse HEAD > .practice/b-3-commit.txt。

    测试没通过？

    读第一条失败信息，让 Claude 改代码，不要让它改测试。

  2. 自查：提交前你把整个 diff 读完了，并且至少让 Claude 纠正过一次。

用 CLAUDE.md 写项目记忆

学完这课，你能写一份项目 CLAUDE.md，并证明新会话会遵守它。

先搞懂

每个会话都从空白的上下文开始，所以同样的交代你可能要说一遍又一遍。项目根目录放一个 CLAUDE.md 就能解决：每次会话开始时，Claude Code 都会读它。

  • 里面放每个会话都该知道的内容：构建和测试命令、约定、项目结构、“总是要做 X”这类规则。要写得短，官方建议不超过 200 行。
  • 把它提交进仓库，这样所有人拿到的都是同一套说明。
  • /init 会根据代码自动写出第一版。
  • Claude 把 CLAUDE.md 当作参考信息，不是必须执行的配置。绝对不能违反的规则要靠钩子（hook）来强制。

CLAUDE.md 只在会话开始时读取。改完以后，要开一个新会话才能确定它用上了新内容。

本页把官方初级第 4 课（让会话不跑偏）放进了推荐加修，所以这里直接从第 5 课接上；第 5 课只要求先学完第 3 课。

跟着做

  1. 在练习仓库里启动 claude，运行：

    /init

    Claude 会读代码，把找到的命令和约定写进 CLAUDE.md。如果它请求批准，就批准。然后在窗口 B 用 cat CLAUDE.md 读一遍。

  2. 用编辑器打开 CLAUDE.md。也可以在窗口 A 输入 /memory，选 Project instructions，也就是本文件夹里的 ./CLAUDE.md。不要选 ~/.claude/ 下面的用户文件，那个会作用于你所有的项目。

    在练习仓库里，/init 可能还写了课程自带的文件：checks/、learn/、capstone/、.github/。把这些内容删掉，关于 npm run check、npm run learn、npm run test:checks 的内容也删掉。如果有“不要在 main 上工作”这类规则，同样删掉：那是给模板仓库用的，不适用于你的副本。npm test 这些其他命令要保留。

  3. 加一条从文件内容上就能看出有没有被遵守的规则。放在 ## Conventions 标题下面；如果没有这个标题，就在文件末尾加上：

    ## Conventions

- Every new source file starts with the line `// Part of linkcheck.`

    意思：每个新建的源代码文件，第一行都写 // Part of linkcheck.

  4. 保存规则原文，后面检查要用；然后提交 CLAUDE.md：

    echo '// Part of linkcheck.' > .practice/b-5-rule.txt
git add CLAUDE.md
git commit -m "Add project instructions for Claude Code"

把重复工作做成技能

学完这课，你能把一套反复使用的工作流程写成项目技能：输入名字就能运行，请求内容匹配时也会自动加载。

先搞懂

技能（skill）就是一个文件夹，里面放一个 SKILL.md 文件。文件开头是一段 YAML 说明（frontmatter），写清这个技能是干什么的；后面是 Claude 要照着做的步骤。项目技能放在 .claude/skills/<名字>/SKILL.md，提交到仓库后，团队里每个人都能用。

技能运行之前，Claude 的上下文里最多只有它的简介（description）。技能有两种触发方式，不管哪种，触发后 Claude Code 都会加载整个文件：

  • 你输入 /技能名，后面可以跟一段内容，这段内容会填进技能正文里的 $ARGUMENTS。
  • 你的请求和技能简介对得上，Claude 自己去加载。

frontmatter 里写 disable-model-invocation: true，技能就只能靠输入名字来触发。部署这类有副作用的流程适合这样设置。

联系你的工作：询盘分级、客户背调，都可以做成这样一个技能。

跟着做

  1. 在练习仓库里下载教程自带的示例技能 five-whys（连问五个为什么，找出根本原因）：

    cd {{DIR}}

curl -fsSL https://raw.githubusercontent.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/main/examples/intermediate/01-first-skill/dot-claude/skills/five-whys/SKILL.md -o .claude/skills/five-whys/SKILL.md
cat .claude/skills/five-whys/SKILL.md

    用之前先把内容读一遍。去掉开头的注释行后，主要是这些：

    ---
name: five-whys
description: Finds the root cause of a bug, failure or recurring problem by asking "why" until the answer is a cause you can fix. Use when the user asks why something keeps happening, or wants the root cause rather than a quick fix.
argument-hint: "[problem]"
---

Find the root cause of this problem: $ARGUMENTS

    后面还有五个编号步骤，以及一条规则 “Don't change any files.”（不要改任何文件）。

  2. 启动 claude，查看技能列表：

整理项目记忆，查看加载了什么

学完这课，你能把项目说明拆成导入文件和分范围规则；Claude 不遵守某条说明时，能查出是哪份说明文件没有加载。

先搞懂

CLAUDE.md 写得太长不好维护，而且每一行都会加载进每个会话。有两种办法把它拆开：

  • 导入（import）：在 CLAUDE.md 里写一行 @docs/conventions.md，被引用的文件会一起加载。这只是让结构更清楚，并不节省上下文。
  • 规则（rule）：放在 .claude/rules/ 下的 Markdown 文件。frontmatter 里写了 paths: 的规则，只有 Claude 处理匹配的文件时才会加载。
说明文件什么时候加载
项目根目录的 CLAUDE.md，以及没写 paths: 的规则会话开始时
被 @路径 导入的文件和导入它的文件一起加载
写了 paths: 的规则Claude 用 Read、Write、Edit 工具读、写或编辑匹配的文件时
自动记忆（Claude 自己记的笔记）会话开始时，加载 MEMORY.md 索引的前 200 行或前 25KB

Claude 不遵守某条说明时，先查这份文件有没有加载。如果加载了，问题多半出在写法上：写得更具体些，并删掉和它冲突的说明。

权限、设置范围与沙箱

学完这课，你能把权限规则放进作用范围合适的设置文件，查看哪些规则正在生效，并打开沙箱，让 Claude 运行的 shell 命令只能写入项目目录、临时目录和你额外加入的目录。

先搞懂

Claude Code 从四个设置文件读取设置。规则写在哪个文件里，决定了它对谁生效：

文件对谁生效适合放什么
~/.claude/settings.json你自己，所有项目个人偏好
.claude/settings.json（提交进仓库）项目里所有人团队规则：Claude 绝对不能读的文件、大家都要跑的命令
.claude/settings.local.json（不进 git）你自己，仅本项目个人例外。对某条命令选 “Yes, and don't ask again”，就会保存在这里
Managed settings（托管设置）组织统一下发的所有人公司政策，你自己的设置覆盖不了

规则的判断顺序是：先看 deny（拒绝），再看 ask（询问），最后看 allow（允许），第一条匹配上的规则说了算。

权限规则管的是 Claude 的各种工具。沙箱则由操作系统在 Claude 运行的 shell 命令外面再加一层边界：默认只能写项目目录、你用户的临时目录，以及你用 --add-dir 或 /add-dir 加进来的目录；联网要经过一个代理，按你允许的域名逐个放行。沙箱默认是关着的。在它的 auto-allow 模式下，沙箱内运行的命令不需要权限确认。

联系你的工作：接真实客户资料之前，先用这一课的方法把能读什么、能写到哪里限定好。

跟着做

  1. 在练习仓库里启动 claude，运行 /status。

    Setting sources 这一行列出了本次会话加载的设置文件。

  2. 新建 .claude/settings.json，写入团队规则：禁止 Claude 读取 .env 文件（这类文件里通常放账号密码），允许直接运行测试命令：

    {
  "permissions": {
    "allow": ["Bash(npm test)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}

    设置文件一改，Claude Code 就会重新加载，不用重启。

  3. /permissions

    allow 规则里有 Bash(npm test)，deny 规则里有那两条 Read。

  4. Run npm test

    测试直接运行，没有弹出权限确认，因为 allow 规则覆盖了这条命令。

  5. 打开沙箱：运行 /sandbox，在 Mode 标签页选 auto-allow。这个设置会保存到你的个人文件 .claude/settings.local.json。

    只看到一个 Dependencies 标签？

    说明沙箱缺少依赖。Mac 自带所需组件；在 Linux 或 WSL 2 上要安装 bubblewrap 和 socat，然后重启 Claude Code，再运行 /sandbox。

  6. 让 Claude 试着在项目外面写文件：

    Run this exact command and show me its output: touch ~/sandbox-probe

    意思：原样运行这条命令并显示输出：在你的用户主目录建一个文件。

    命令没有弹确认就运行了，但执行失败。Mac 上的报错是 Operation not permitted。

    如果 Claude 提出要在沙箱外重试，拒绝。

自己练一遍

  1. 原课的这一部分是在你自己的仓库里再做一遍。只用练习仓库的话，完成下面三步就行。以后要在装客户资料的真实文件夹里用 Claude Code，再按同样的方法做一次。

  2. 确认 .claude/settings.json 只允许一条测试命令，并且同时禁止读取 .env 和 .env.*。然后提交：

    git add .claude/settings.json
git commit -m "Add team permission rules"

  3. 运行 git status，确认 .claude/settings.local.json 没有被列出来。Claude Code 创建它时会自动把它排除在 git 之外。

检查过关

  1. git show HEAD:.claude/settings.json | jq .permissions

    第一项因为规则太宽没通过？

    把它换成具体的那一条命令。比如 Bash(npm *) 会让 Claude 不问你就运行任何 npm 命令。

  2. 自查：Claude 运行 touch ~/sandbox-probe 时没有先问你，而且失败了。

容易踩的坑

沙箱只管 shell 命令。Claude 的文件工具和网页工具在沙箱外运行，受权限规则约束；钩子和本地 MCP 服务器也在沙箱外运行，拥有你的全部权限。另外，沙箱启动失败时，Claude Code 默认会在没有沙箱的情况下继续运行命令，除非把 sandbox.failIfUnavailable 设为 true。

单独一条 Read deny 规则，能拦住 Claude 的文件工具和它认得的文件命令（比如 cat），但拦不住自己去打开文件的脚本。打开沙箱后，deny 的路径会同时加进沙箱的禁读列表，沙箱里的命令和它们启动的进程也就都读不到了。

用 MCP 连接外部工具

学完这课，你能先给自己接入一个 MCP 服务器，再把它锁定到一个固定版本，按项目范围共享给项目里的所有人。

先搞懂

MCP（Model Context Protocol，模型上下文协议）让 Claude Code 能使用另一个程序提供的工具，这个程序叫 MCP 服务器。本课用的是 Google 出的 Chrome DevTools MCP：它在你电脑上运行，让 Claude 能在 Chrome 里打开网页、读控制台输出、截图。

范围谁能用存在哪里
Local（默认）你自己，仅本项目~/.claude.json
Project项目里所有人项目根目录的 .mcp.json，提交进仓库
User你自己，所有项目~/.claude.json

在交互式会话里，项目里的服务器要先经过你批准才会被使用。

数据外流提醒：Chrome DevTools MCP 默认会向 Google 发送使用统计，可能把性能追踪的网址发给 Google 的 CrUX 接口，还会联网检查 npm 更新。本课每次运行都把这三项关掉。即便如此，Claude 打开的网页仍然是从网上加载的，而且这个服务器能让 Claude 看到那个浏览器里的所有内容。

需要提前装好 Chrome，以及 Node.js 自带的 npm。

跟着做

  1. 在练习仓库里准备一个要查看的网页：

    cd {{DIR}}
cat > .practice/demo.html <<'EOF'
<!doctype html>
<title>Linkcheck demo</title>
<h1>Linkcheck demo</h1>
<script>console.warn('demo warning from the page');</script>
EOF

  2. 按 Local 范围给自己接入服务器。版本号固定为 1.10.1；--isolated 让浏览器使用一个临时配置；另外两个参数和环境变量负责关掉那三项数据外流。-- 后面的部分是服务器自己的启动命令：

    claude mcp add --env CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS=1 --transport stdio chrome-devtools -- npx -y chrome-devtools-mcp@1.10.1 --isolated --no-usage-statistics --no-performance-crux
  3. claude mcp get chrome-devtools

    显示它所在的范围（这里是 local）和服务器状态。

  4. 启动 claude，运行 /mcp，能看到 chrome-devtools 和它提供的工具。然后提问：

    Use the chrome-devtools tools to open .practice/demo.html as a file: URL, and tell me its title and console messages.

    意思：用 chrome-devtools 工具以 file: 地址打开这个网页，告诉我它的标题和控制台消息。

    弹出一个 Chrome 窗口，Claude 报告标题是 Linkcheck demo，并给出那条控制台警告。如果是 Manual 模式，每个工具第一次使用时会先问你要权限。

自己练一遍

  1. 删掉本地范围的那份配置，否则它会优先于同名的项目服务器：

    claude mcp remove chrome-devtools -s local

  2. 在仓库根目录新建 .mcp.json，把下面每个 TODO 换成示例命令里对应的值：

    {
  "mcpServers": {
    "chrome-devtools": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "TODO: the package at an exact version", "--isolated", "TODO: no usage statistics", "TODO: no CrUX lookups"],
      "env": { "TODO: the variable that turns off update checks": "1" }
    }
  }
}
    想对一下答案？

    四个 TODO 依次是：chrome-devtools-mcp@1.10.1、--no-usage-statistics、--no-performance-crux、CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS。

  3. 提交：git add .mcp.json，再 git commit -m "Share the chrome-devtools MCP server"。

  4. 启动 claude。它会提示项目里发现了新的 MCP 服务器，选择使用它。之后 /mcp 会显示它已连接。

  5. 让 Claude 截图：

    Use the chrome-devtools tools to open .practice/demo.html and save a screenshot of it to .practice/i-7-page.png

检查过关

  1. file .practice/i-7-page.png
npm run check -- i-7

    显示 PNG image data，检查全部 PASS。

    第一项没通过？

    把每个参数和示例命令逐一对比。写成 @latest 不算固定版本。

    没有生成截图？

    运行 /mcp 看服务器有没有连上。错过了批准提示的话，可以在 /mcp 里批准；如果之前点了拒绝，运行 claude mcp reset-project-choices，再重新启动 claude。

  2. 自查：批准之后，/mcp 显示 chrome-devtools 已连接。

容易踩的坑

用 claude -p 写脚本运行时，Claude Code 会不经询问就加载项目里的 MCP 服务器。在任何仓库里写脚本调用 Claude Code 之前，先读一遍它的 .mcp.json。

第三方 MCP 服务器能在你电脑上运行代码，或者给 Claude 加上新工具。安装前先审一下，原教程不负责审核它们。

命令 / 按键作用课

术语

Session 会话
一次和 Claude Code 的对话。会话越长，上下文越满。
Context 上下文
Claude 当前“记得”的全部内容：对话、读过的文件、加载的说明。
Permission mode
权限模式，决定 Claude 改文件、跑命令前要不要问你。
Plan mode
计划模式，Claude 先出方案，你批准后才动手改文件。
CLAUDE.md
项目记忆文件，每次会话开始时读取。
Rule 规则
.claude/rules/ 下的说明文件，写了 paths: 就只在处理匹配文件时加载。
Skill 技能
存成文件的一套工作说明，输入名字调用，请求匹配时也会自动加载。
Hook 钩子
在会话的固定时点必定执行的命令，用来强制执行规则。
Sandbox 沙箱
由操作系统限制 Claude 运行的 shell 命令能写到哪里、能连哪些网站。
MCP
让 Claude Code 使用外部程序所提供工具的协议，例如浏览器、数据库、某个服务的接口。

第 4 课 CLAUDE.md

公司与产品画像

写清 AICRANE 与 AIMIX 的产品范围、达曼办公室的安装和备件能力、S/A/B/C 评级标准和输出格式。开新会话验证 Claude 是否照着回答。不写银行信息、合同金额和私人联系方式。

第 5 课 技能

“询盘分级”技能

把每次分析询盘时重复交代的要求写成技能，输出固定栏目：核心需求、紧迫度、决策链、产品匹配、风险、下一步、英文回复草稿。

第 7 课 权限与沙箱

给客户资料文件夹上锁

禁止读取 .env 这类含账号密码的文件，打开沙箱，再用 /permissions 确认规则已生效。

第 8 课 MCP

接外部工具做背调

学会接入 MCP 服务器后，可以连接你已授权的表格、浏览器等工具来整理跟进台账。连接了就等于授权它读取；对外发送、发布仍然要你明确确认。

以后再学

  • 初级第 4 课 让会话不跑偏：一次处理很多询盘、会话变长时再补，学 /context、/clear、/compact、/rewind、/resume。
  • 中级第 3 课 选择模型与思考力度，以及第 8 课 插件：前者帮你省时间，后者可以直接装现成的功能包。
  • 中级第 5、6 课 钩子、子代理：要强制执行某条规则，或把任务分给专门的助手时再学。
  • 高级课程：想让流程定时自动跑（比如每周汇总跟进），或者要给团队统一配置时再学。
