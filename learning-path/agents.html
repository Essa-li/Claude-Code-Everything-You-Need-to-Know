什么是 AI 智能体

学完这课，你能说清楚什么是 AI 智能体、它和普通 AI 应用有什么不同，判断什么时候该用（什么时候不该用）智能体，并为一个真实问题画出智能体的基本设计。

先搞懂

原课程给了一句话的定义：AI 智能体，是让大模型真正“做事”的系统：给它工具和知识，让它作用于外部世界，而不只是回答提示。

它是一个系统，由几部分配合工作。每个智能体的核心都有三样东西（原课程用旅行预订智能体举例）：

  • 环境：智能体工作的地方，比如预订平台本身。
  • 传感器：它感知环境当前状态的方式，比如查看酒店房态、航班价格。
  • 执行器：它采取行动的方式，比如预订房间、发确认信息、取消预订。

在这三样之外，还有几个关键部分：

  • 大模型：能听懂自然语言、根据上下文推理，把模糊的请求变成具体的行动计划。
  • 执行动作：没有智能体系统，大模型只会生成文字；在智能体里，它能搜索数据库、调用接口、发消息。
  • 工具访问：能用哪些工具，取决于它运行的环境和开发者给它的能力。旅行智能体可能能查航班，却不能改客户记录。
  • 记忆与知识：短期记忆是当前对话，长期记忆是客户数据库、过去的交互，比如记住你喜欢靠窗座位。

智能体有不同类型。原课程按旅行预订的例子列了七种：

类型特点旅行智能体例子
简单反射按写死的规则做，没有记忆和规划看到投诉邮件就转给客服
基于模型的反射在内部维护一个环境模型，随变化更新跟踪历史票价，标出突然涨价的航线
目标驱动有明确目标，一步步规划怎么达成订好整趟行程：航班、租车、酒店
效用驱动不只找到一个方案，而是权衡得失找最优平衡价格和便利，挑最合你偏好的行程
学习型根据反馈不断改进根据行程后的调查调整以后的推荐
分层上层智能体拆任务，交给下层智能体“取消行程”拆成取消航班、酒店、租车
多智能体系统多个独立智能体协作或竞争分别负责酒店、航班、娱乐的几个智能体

什么时候该用智能体：能用，不代表就该用。原课程说下面三种情况特别适合：

  • 开放式问题：没法提前写死每一步，需要它自己探索解决路径。
  • 多步骤流程：任务要多轮、用多种工具，不是一次查询或生成就能完成。
  • 持续改进：系统要根据用户反馈或环境信号不断变聪明。

搭智能体的三块基础：

  • 智能体开发：第一步是定义它能做什么，也就是它的工具、动作和行为。原课程用 Microsoft Foundry Agent Service 作为主要平台。
  • 智能体模式：智能体要跨多个步骤行动，没法每个提示都手写，所以要用可复用的提示和编排策略，这就是“智能体模式”。整门课都围绕最常用的模式展开。
  • 智能体框架：现成的模板、工具和基础设施，帮你接工具、观察和调试智能体、让多个智能体协作。原课程重点讲 Microsoft Agent Framework（MAF）。

原课程的定义：AI 智能体框架是一种软件平台，用来简化智能体的创建、部署和管理。它提供现成的组件、抽象和工具，把开发中的常见难题用标准方法解决掉，让开发者专心做自己应用独特的部分。

智能体框架和普通 AI 框架有什么不同：普通 AI 框架能让应用更好，比如个性化推荐（Netflix 按观看记录推荐）、自动化（客服聊天机器人处理常见问题）、更好的用户体验（Siri 听懂语音指令）。智能体框架更进一步，它要造出能和用户、其他智能体、环境互动，去完成目标的智能体。原课程列了三项关键能力：

  • 协作与协调：多个智能体一起工作、互相沟通，解决复杂任务。
  • 任务自动化与管理：自动跑多步骤流程，在智能体之间分派和动态管理任务。
  • 理解上下文并适应：理解情境，适应变化，根据实时信息做决定。

怎么快速做原型、迭代、改进：原课程说大多数框架都有三样共同的东西：

做法是什么团队怎么用
模块化组件现成的 AI 连接器、工具定义、智能体管理等直接拼出能用的原型，不用从零写
协作工具造多个各有分工的智能体，比如一个取数据、一个做分析测试并改进协作流程，提高整体效率
实时学习反馈循环：根据互动和结果调整行为能力持续改进

Microsoft Agent Framework（MAF）：一个精简的 SDK（开发工具包），用 FoundryChatClient 搭智能体。原课程讲了四个核心概念：

  • 智能体：配置名称、指令和工具；能处理用户消息、根据对话自动调用工具、在多轮对话里保持状态。
  • 工具：用 Python 函数定义，创建智能体时注册进去，智能体会自动调用。
  • 多智能体协调：造几个分工不同的智能体，比如一个“规划者”拆步骤、一个“执行者”去执行。
  • Azure 身份集成：用 Azure 登录认证，不用直接管理 API 密钥。

Microsoft Foundry Agent Service：原课程说它是较新的服务，在 Microsoft Ignite 2024 上推出，目前是公开预览版，支持用 Python 和 C# 构建智能体。它能用更灵活的模型（包括直接调用 Llama 3、Mistral、Cohere 这类开源模型），有更强的企业安全机制和数据存储方式。核心概念：

  • 智能体：在 Microsoft Foundry 里像一个“智能”微服务，可以回答问题（RAG）、执行操作或完全自动化工作流。
  • 线程和消息：线程代表智能体和用户之间的一次对话，用来跟踪进展、保存上下文；消息可以是文字、图片或文件。
  • 和 MAF 配合：用 MAF 搭好的智能体，可以通过 Agent Service 部署到生产环境。

两者的区别和怎么选：

名称是什么适合
Microsoft Agent Framework构建智能体的 SDK：工具调用、会话管理、Azure 身份想快速上手，几行代码定义带工具和指令的智能体
Microsoft Foundry Agent ServiceFoundry 里的智能体平台和部署服务，内置连接 Azure OpenAI、Azure AI Search、Bing 搜索、代码执行需要企业级部署，并接入搜索、代码执行等 Azure 能力

原课程给“还是拿不定”的建议：先用 MAF 搭智能体，需要在生产环境部署和扩展时，再用 Agent Service。

能不能直接接已有的 Azure 工具：能。原课程说尤其是 Agent Service，本来就为配合其他 Azure 服务而设计，比如 Bing、Azure AI Search、Azure Functions；MAF 也能通过 FoundryChatClient 和 Azure 身份，在工具里直接调用 Azure 服务。

AI 智能体设计原则

学完这课，你能说清楚智能体的设计原则是什么、落实这些原则的三条准则（透明、控制、一致），并用它们去设计一个智能体。

先搞懂

原课程说，生成式 AI 的设计里，模糊是特点，不是缺陷，所以工程师常常不知道从哪儿下手。为此它给了一套以人为中心的用户体验设计原则。它们不是规定死的架构，而是团队设计智能体体验时的起点。

总的来说，智能体应该：

  • 扩展和放大人的能力（头脑风暴、解决问题、自动化等）；
  • 补上知识缺口（让人快速了解一个领域、翻译等）；
  • 按我们各自喜欢的方式，促进和支持与他人的协作；
  • 让我们成为更好的自己（比如像生活教练一样帮人成长）。

原则分三组。第一组是空间：智能体在哪里工作，怎么在现实和数字世界里与人打交道。

  • 连接，而不是取代：把人和其他人、事件、可用的知识连起来，促进协作。智能体让人更紧密，不是为了取代或贬低人。
  • 容易找到，有时又看不见：大部分时间在后台工作，只在相关、合适的时候提醒你；授权用户在任何设备上都能找到它；支持声音、语音、文字等多种输入输出；能在前台和后台、主动和被动之间切换。即使在后台，它的处理过程和与其他智能体的协作，对用户也要透明、可控。

第二组是时间：智能体怎么跨越过去、现在和未来与人互动。

时间原则意思
过去回顾历史，包括状态和上下文分析更丰富的历史数据，把过去的事和眼前的情况联系起来
现在提示多于通知不只是发一条固定的通知，而是简化流程、在对的时刻引导注意力，并贴合用户意图
未来适应和进化适应不同设备和用户习惯，可以自由定制，在持续互动中不断进化

第三组是核心：接受不确定性，但要建立信任。

  • 智能体有一定的不确定性是正常的，不确定性本身就是设计的关键要素。
  • 信任和透明是智能体设计的基础。
  • 人来决定智能体什么时候开、什么时候关，它的状态要始终清楚可见。

落实这些原则的三条准则：

  1. 透明：告诉用户这里用了 AI、它怎么工作（包括它过去做过什么），以及怎么反馈、怎么修改系统。
  2. 控制：让用户能定制、设置偏好、个性化，能控制系统和它的属性，包括让它“忘掉”某些东西。
  3. 一致：在不同设备上提供一致的体验；尽量用大家熟悉的界面元素（比如用麦克风图标表示语音）；尽量减轻用户的认知负担（比如回答简洁、配图、提供“了解更多”）。

原课程用旅行智能体演示怎么用这三条：

  • 透明：告诉用户这是 AI 智能体；给出入门说明（比如一句问候、示例提示）；展示用户过去问过的问题；说明怎么反馈（点赞点踩、“发送反馈”按钮）；讲清楚它有哪些使用或话题限制。
  • 控制：说明创建后怎么修改它（比如系统提示）；让用户选它说话多详细、什么文风、哪些话题不该谈；让用户能查看和删除相关的文件、数据、提示和历史对话。
  • 一致：分享提示、上传文件或图片、标记某人某物的图标都用标准、好认的样式，比如回形针表示上传文件，图片图标表示上传图片。

本课的示例笔记本还从代码角度演示了三个基础做法：写清楚指令（它是谁、做什么、怎么做）、结构化输出（规定好返回数据的格式，方便其他系统使用）、单一职责（每个智能体只做一件事，比如一个只挑目的地，一个只排行程）。“跟着看”里会带你读。

工具使用设计模式

学完这课，你能说清楚什么是工具使用设计模式、它适合哪些场景、实现它需要哪些关键部分，以及用工具时怎样让智能体保持可信。

先搞懂

工具使用设计模式：让大模型能和外部工具打交道，去完成具体目标。工具就是智能体可以执行的代码，可以是一个简单函数（比如计算器），也可以是调用第三方服务的接口（比如查股价、查天气）。在智能体里，工具是在模型生成“函数调用”之后才被执行的。

原课程列了五类常见用途：

  • 动态信息检索：查外部接口或数据库拿最新数据，比如查 SQLite 数据库做分析、查股价或天气。
  • 代码执行与解释：运行代码或脚本，解数学题、生成报告、做模拟。
  • 工作流自动化：接上任务调度、邮件服务、数据管道，把重复或多步骤的流程自动化。
  • 客户支持：和 CRM、工单平台、知识库交互，解决用户问题。
  • 内容生成与编辑：借助语法检查、文本摘要、内容安全评估等工具协助创作。

实现这个模式需要六个部分：

  • 函数/工具说明（schema）：每个工具的名字、用途、必填参数、预期输出。大模型靠它知道有哪些工具、该怎么调用。
  • 函数执行逻辑：根据用户意图和上下文，决定何时调用哪个工具。
  • 消息处理：管理用户输入、模型回复、工具调用、工具结果之间的来回。
  • 工具集成框架：把智能体接到各种工具上，不管是简单函数还是复杂的外部服务。
  • 错误处理与校验：工具失败、参数不对、返回意外结果时怎么办。
  • 状态管理：记住对话上下文、之前的工具调用，让多轮对话前后一致。

函数调用是让大模型用工具的主要方式（所以“函数”和“工具”常混着说）。原课程用“查某个城市当前时间”演示了整个过程：

  1. 把所有可用函数的说明（schema）和用户问题一起发给模型；
  2. 模型对比问题和说明，挑出最合适的函数，返回的是函数名和参数，不是最终答案，比如 get_current_time，参数 location="San Francisco"；
  3. 你的代码真正执行这个函数，把结果发回模型；
  4. 模型用这个结果回答用户：“旧金山现在是上午 9:24。”

要做到这一点需要三样东西：支持函数调用的模型（不是所有模型都支持）、函数说明、每个函数的代码。

从零写函数调用有点麻烦，所以要用框架。原课程介绍了两个：

  • Microsoft Agent Framework：用 @tool 标记一个普通函数，框架自动生成说明发给模型，并处理模型和代码之间的来回。工具也可以来自 M C P 服务器：服务器连同说明一起发布自己的工具，框架像加载本地函数一样加载它们（原课程示例接了一个网页搜索服务器，并提醒：模型写的查询会发给那台服务器）。
  • Microsoft Foundry Agent Service：全托管服务，工具调用在服务端自动完成，用“线程”（threads）保存对话历史，并自带现成工具。工具分两类：知识类（Bing 搜索、文件搜索、Azure AI Search）和动作类（函数调用、代码解释器、OpenAPI 定义的工具、Azure Functions），可以组合成一个工具集（toolset）。

用工具时怎样保持可信：原课程举的例子是大模型动态生成 SQL 查询，担心 SQL 注入或删改数据库。办法是把数据库访问权限配成只读（比如只给 SELECT 角色），并让程序运行在安全环境里。企业里通常会把业务系统的数据抽到一个只读的数据库或数据仓库，让智能体只能读、不能改。

Agentic RAG：会自己查资料的智能体

学完这课，你能说清楚 Agentic RAG 和普通“先检索再回答”的区别，理解它“查、评估、再查”的循环、自我纠错和自主性的边界，并判断哪些场景适合用它。

先搞懂

RAG 是“检索增强生成”：先从外部资料里查出相关内容，再让大模型据此回答。普通 RAG 是一条固定流水线：查一次，读一次，答一次。

Agentic RAG 不一样：大模型在从外部资料取信息的同时，自己规划下一步。它会反复调用大模型，中间穿插工具调用和结构化输出；每一轮都评估查到的结果，决定要不要改写查询、换一个工具，一直循环到得出满意的答案。

原课程把这种工作方式叫“制作者-检查者”（maker-checker）风格：先做出来，再检查，不行就再来。它能提高正确率，处理写坏了的数据库查询（比如把自然语言转成 SQL 时出错），保证结果质量。不需要复杂的编排框架，一个简单的循环就够了：调用大模型 → 用工具 → 再调用大模型 → ……

掌控推理过程是“智能体式”的关键。普通 RAG 往往要人提前规定好查什么、什么时候查；智能体式的系统自己决定怎么解决问题。原课程的例子：让它制定一个产品上市策略，它会自己决定：

  1. 用 Bing 网页搜索查当前的市场趋势报告；
  2. 用 Azure AI Search 找相关的竞争对手数据；
  3. 用 Azure SQL 数据库关联历史内部销售数据；
  4. 用 Azure OpenAI 把这些整合成策略；
  5. 检查策略有没有漏洞或矛盾，必要时再查一轮。

这些步骤都是模型决定的，不是人写死的。

循环的五个环节：

  • 初始调用：把用户的目标交给大模型。
  • 调用工具：发现缺信息或指令含糊，就选一个工具或检索方式（比如向量检索私有数据、或结构化的 SQL 查询）去补充。
  • 评估与改进：看返回的数据够不够；不够就改写查询、换工具、调整方法。
  • 重复直到满意：直到有足够的证据给出有依据的回答。
  • 记忆与状态：系统记得之前试过什么、结果如何，避免原地打转。

出错时怎么自我纠正：查到无关文档、查询写错时，它可以：

  • 迭代和重新查询：不交出低价值的回答，而是换搜索策略、改写数据库查询、看别的数据集。
  • 用诊断工具：调用专门的函数来检查推理步骤、确认数据是否正确（原课程提到 Azure AI Tracing 这类可观测工具）。
  • 求助人工：高风险或反复失败时，标出不确定，请人指导；人给出纠正后，它在后续过程中吸取这个教训。

自主性有边界：Agentic RAG 不是通用人工智能。它的能力被限定在开发者给它的工具、数据源和规则之内，不能自己发明工具，也不能越出设定的领域。原课程列了三点：

  • 限于特定领域：在已知领域里完成用户定的目标。
  • 依赖基础设施：能力取决于开发者接入的工具和数据。
  • 遵守护栏：伦理准则、合规规则、业务政策始终约束着它。

构建可信赖的 AI 智能体

学完这课，你能用“系统消息框架”写出更可靠的智能体指令，认出智能体面临的五类主要威胁和对应的防范办法，并用“人在回路中”让关键动作经过人的批准。

先搞懂

原课程说的安全，意思是智能体按设计去做事。作为搭建者，我们有方法和工具来尽量做到这一点。本课讲三块：系统消息框架、理解威胁、人在回路中。

系统消息（system message）是给大模型定下规则、指令和准则的那段话。对智能体来说它更重要，因为智能体要靠非常具体的指令去完成任务。原课程给了一个能批量、持续改进系统消息的四步框架：

  1. 写一段“元系统消息”：一个模板，交给大模型，让它负责生成智能体的系统消息。原文大意：你是创建 AI 助手的专家，会拿到公司名、角色、职责等信息，请写出尽量详细、结构清楚的系统提示。
  2. 写一段基础提示：说明智能体的角色、要完成的任务和其他职责。原课程例子：Contoso Travel 的旅行顾问，能查航班、订航班、问座位和时间偏好、取消已订航班、提醒延误或取消。
  3. 把两者交给大模型：元系统消息作为系统消息，基础提示作为输入，得到一份结构完整的系统消息（公司、角色、目标、主要职责、语气风格、交互要求、补充说明）。
  4. 迭代改进：很少有一次就完全好用的系统消息。改基础提示、重新生成、对比结果，一点点改好。

理解威胁：原课程列了五类（并说明这只是其中一部分）：

威胁是什么怎么防
任务与指令通过提示或篡改输入，改变智能体的指令或目标输入校验和过滤；限制对话轮数
访问关键系统智能体能碰敏感数据时，攻击它和这些系统之间的通信按需授权；通信要安全；身份验证和访问控制
资源和服务过载借智能体大量请求外部服务，导致系统故障或高额费用限制它对服务的请求次数；限制对话轮数和请求数
知识库投毒不直接攻击智能体，而是篡改它要用的知识库和数据定期核查数据；只让可信的人修改
连锁错误一处错误传到它连接的其他系统，越扩越大、难以排查在受限环境（如 Docker 容器）中运行；设回退和重试机制

人在回路中（Human-in-the-loop）：在智能体运行过程中，让用户能给反馈。用户相当于多智能体系统里的一员，可以批准或终止正在运行的流程。README 里的示例很简单：智能体先写一首四行诗，再问用户 APPROVE 还是 REJECT。

本课的示例代码在这个基础上更进一步，讲了生产中常用的三件事：

  • 动作前把关：在智能体执行有风险的一步之前就拦下来请人批准，而不是事后再看。事后批准时，邮件可能已经发出去了。
  • 风险分级：低风险（只读，如查资料）自动执行并记录；中风险（如设提醒）自动执行，但每天集中复核；高风险（对外或不可撤销，如发邮件、扣款）必须等人批准。认不出的动作默认按中风险处理，而不是低风险。
  • 审计日志和修改循环：每次批准或拒绝都记成一条带时间、动作、风险级别、理由的记录；被拒绝时，把拒绝理由交回智能体，让它换一个方案再提。

原课程的结论：可信的智能体需要仔细的设计、可靠的安全措施和持续迭代。用结构化的元提示、理解威胁并采取防范措施、加上人在回路中，智能体才能既安全又有效。随着 AI 发展，持续关注安全、隐私和伦理，是建立信任的关键。

规划设计模式

学完这课，你能给智能体定一个清楚的总目标，把复杂任务拆成有顺序的子任务并交给合适的智能体，说出为什么计划要用结构化格式输出，并知道情况变了时怎样重新规划。

先搞懂

这一课讲规划：现实中的大多数任务太复杂，一步做不完。智能体需要先有一个简明的总目标来指导它的规划和行动。原课程的例子是“生成一份三天的旅行行程”：说起来简单，但还要细化。目标越清楚，智能体（以及一起工作的人）就越能聚焦在正确的结果上，比如一份包含航班选项、酒店推荐和活动建议的完整行程。

任务拆解：大任务拆成更小、各有目标的子任务后就好管理了。旅行行程可以拆成：

  • 订机票
  • 订酒店
  • 租车
  • 个性化定制

每个子任务可以交给专门的智能体或流程：一个专找最划算的航班，一个专管酒店。最后由一个负责协调的“下游”智能体把结果汇总成一份完整行程交给用户。这种模块化的做法还方便以后逐步增强，比如再加一个美食推荐或本地活动推荐的智能体。

结构化输出：大模型能输出 JSON 这样的结构化结果，下游的智能体或服务更容易解析和处理。在多智能体的场景里特别有用：拿到计划后就能直接按计划派活。原课程的例子里，规划智能体的系统提示列出了可用的智能体（订机票、订酒店、租车、订活动、目的地信息、默认智能体），它输出的计划包含：

  • main_task：总任务，比如“规划一次从新加坡到墨尔本的家庭旅行”；
  • subtasks：子任务列表，每条写明 task_details（要做什么）和 assigned_agent（交给谁）；
  • is_greeting：这条消息是不是只是打招呼。

规划智能体 + 多智能体编排：用户发来请求（比如“我的旅行需要一个酒店方案”）后，规划智能体会：

  1. 根据系统提示（里面有可用智能体的说明）把请求变成一份结构化的计划；
  2. 查看智能体注册表：里面列着各个智能体以及它们提供的工具；
  3. 按子任务的数量派发：只有一个子任务就直接发给对应的专门智能体，多个子任务就通过一个“群聊管理器”让多个智能体协作；
  4. 最后把生成的计划总结一下，让用户看得明白。

迭代规划：这对应本课开头说的“处理动态任务和意外输入”。有些任务需要来回调整，前一个子任务的结果会影响下一个。比如订机票时发现了意料之外的数据格式，就要先调整策略，再去订酒店。用户的反馈（比如有人决定更想要早一点的航班）也会触发局部重新规划。原课程的做法是：重新规划时把用户历史和之前的计划一起作为上下文交给规划智能体，再把新任务派给对应的智能体。这样最终方案才能贴合现实约束和用户不断变化的偏好。

本课小结：规划器能从已定义好的智能体里动态挑选，把任务拆开并分配出去执行。这里有个前提：假设各个智能体已经能用到完成任务所需的函数和工具。除了这些智能体，还可以加入反思、总结、轮流对话等其他模式。原课程推荐延伸阅读 Magentic One：它的编排者会为任务制定计划、委派给可用的智能体，还会跟踪任务进度，按需重新规划。

多智能体设计模式

学完这课，你能判断什么场景适合用多个智能体，说出多智能体相比单个智能体的好处，并说清实现多智能体模式要考虑的几块基础，包括怎样看清智能体之间的交互。

先搞懂

原课程的一句话定义：多智能体是一种设计模式，让多个智能体一起工作，达成一个共同的目标。这种模式在机器人、自主系统、分布式计算等很多领域都有广泛应用。

什么场景适合用多智能体：原课程列了三种：

  • 工作量大：大任务拆成小任务分给不同的智能体，并行处理，更快完成。例子：大规模数据处理。
  • 任务复杂：拆成子任务，每个智能体专攻一个方面。例子：自动驾驶里，不同智能体分别管导航、障碍物检测、和其他车辆通信。
  • 需要多种专长：不同智能体各有所长，比一个智能体处理得更好。例子：医疗里分别负责诊断、治疗方案、患者监测。

多智能体比单个智能体好在哪：简单任务用一个智能体就行，复杂任务用多个有三个好处：

  • 专业化：每个智能体专做一件事。一个什么都能做的智能体，遇到复杂任务可能会搞不清该做什么，甚至去做它并不擅长的事。
  • 可扩展：加智能体比让一个智能体越背越多更容易扩展。
  • 容错：一个智能体出问题，其他的还能继续工作。

原课程用旅行预订打比方：单个智能体要自己找航班、订酒店、租车，手里要有所有工具，系统会变得庞大、难维护；多个智能体分别负责航班、酒店、租车，更模块化。就像夫妻店一个人包揽所有环节，连锁加盟店不同的人负责不同环节。

看清智能体之间的交互：这对调试、优化、保证整个系统有效都必不可少。比如旅行预订可以做一个看板，显示每个智能体的状态、用户的偏好和约束、智能体之间的交互。具体有三类手段：

  • 日志和监控：每个动作都记一笔：哪个智能体、做了什么、什么时间、结果如何。
  • 可视化：比如画一张信息在智能体之间流动的图，帮你找出瓶颈和低效的地方。
  • 性能指标：比如完成任务用了多久、单位时间完成多少任务、推荐准不准。

三种具体的多智能体模式：

  • 群聊：多个智能体在一个“群”里互相发消息、回应。可以所有消息都经过一个中心服务器转发（集中式），也可以直接互发（去中心化）。典型用途：团队协作、客服、社交。
  • 交接（hand-off）：每个智能体代表工作流里的一个任务或一步，按预先定好的规则把任务交给下一个。典型用途：客服、任务管理、工作流自动化。
  • 协同过滤：几个各有专长的智能体一起给用户做推荐。例子：用户想知道买哪只股票，一个是行业专家，一个懂技术分析，一个懂基本面分析，合起来给出更全面的建议。

场景：退款流程。原课程把可能用到的智能体分成两类：

  • 退款流程专用：客户智能体（发起退款）、卖家智能体（处理退款）、支付智能体（退钱）、解决智能体（处理过程中出现的问题）、合规智能体（确保符合法规和政策）。
  • 通用（业务其他地方也能用）：运输、反馈、升级、通知、分析、审计、报告、知识库、安全、质量。比如运输智能体既能用于退货，也能用于正常发货；升级智能体任何需要上报的流程都能用。

原课程的作业就是照这个思路，为客户支持流程设计一个多智能体系统，并提醒：你需要的智能体可能比你想的多。

反过来想：什么时候一个智能体就够。原课程的知识测试提醒：如果一套指令和工具就能搞定，不需要专家之间交接，单个智能体通常更合适。最适合多智能体的，是像退款这样需要欺诈审核、支付、合规等不同角色，各有自己的工具，结果还要互相协调的流程。

生产环境中的智能体：可观测性与评估

学完这课，你能说清楚智能体上线后要“看见”什么（跟踪、跨度和关键指标）、怎么系统地评估它（离线评估和在线评估），以及有哪些控制成本的办法，并为自己的业务智能体做一份监控和评估方案。

先搞懂

智能体从试验品变成真正在用的系统后，就必须能看懂它的行为、监控它的表现、系统地评估它的输出。原课程的目标是：把“黑盒子”智能体变成透明、可管理、可靠的系统。没有可观测性，智能体的内部状态和推理是看不见的；有了它，智能体就成了“玻璃盒子”。

可观测性工具（原课程举了 Langfuse 和 Microsoft Foundry）通常用两个概念记录智能体的运行：

  • 跟踪（Trace）：一个完整的智能体任务，从开始到结束，比如处理一次用户提问。
  • 跨度（Span）：跟踪里的单个步骤，比如调用一次大模型、检索一次数据。

为什么上线后可观测性是必需品，原课程给了四个理由：

  • 调试和找根因：出错或输出异常时，跟踪能帮你定位问题出在哪一步，尤其是有多次模型调用、工具调用和条件判断的复杂智能体。
  • 控制延迟和成本：大模型和外部接口按 token 或按次计费，可观测性能精确记录每次调用，找出又慢又贵的环节。
  • 信任、安全与合规：它留下智能体行为和决定的审计记录，可以用来发现提示注入、有害内容、个人身份信息（PII）处理不当等问题。
  • 持续改进：上线后的数据是迭代的基础，在线发现的问题可以反过来用于离线试验和改进。

要盯的关键指标（原课程说，几种指标组合起来才能全面反映智能体的健康状况）：

指标看什么原课程的例子
延迟响应有多快换更快的模型或并行调用来提速
成本每次运行花多少钱调五次模型只换来一点提升，值不值
请求错误接口或工具调用失败多少服务商 A 宕机就切到备用的 B
用户反馈点赞点踩、打星、评论持续差评说明出了问题
隐性反馈用户的行为反复问同一个问题、点重试
准确率输出对不对、合不合要求先定义成功，再把跟踪标成成功或失败
自动评估用模型或开源库打分让大模型判断是否有用、准确

给智能体“装仪表”（instrument）：要收集跟踪数据，就要让代码发出跟踪和指标。原课程说 OpenTelemetry（OTel）已成为大模型可观测性的行业标准，Microsoft Agent Framework 原生集成了它。除了自动生成的跨度，还可以手动创建跨度，并给跨度加上自定义属性（也叫标签或元数据），比如 user_id、session_id、model_version，方便调试和分析。

评估是分析这些数据、做测试，判断智能体表现得好不好、怎么改进。智能体的输出不是每次都一样，而且会随更新或模型变化而“漂移”，所以要定期评估。分两类，互相补充：

  • 离线评估：在受控环境里，用已知正确答案的测试集来跑（比如 100 道有标准答案的数学应用题）。可重复、指标清楚，是上线前的最低要求。难点是测试集要全面、要不断补充新的边缘案例；小的“冒烟测试”集用来快速检查，大的集合看整体表现。
  • 在线评估：在真实使用中持续监控，比如成功率、满意度，也可以做影子测试或 A/B 测试。好处是能抓到实验室里想不到的情况和模型漂移；难点是真实交互很难拿到可靠的评分。

很多团队用一个循环把两者连起来：离线评估 → 上线 → 在线监控 → 收集新的失败案例 → 加进离线测试集 → 改进智能体 → 重复。

常见问题和可能的解决办法（原课程的表格）：

问题可能的解决办法
执行任务不稳定把提示写清楚、目标明确；看能否拆成子任务交给多个智能体
陷入无限循环设清楚的终止条件；复杂推理任务换擅长推理的大模型
工具调用效果差在智能体之外单独测试工具输出；改进参数、提示和工具命名
多智能体不稳定让每个智能体的提示具体且互不重叠；用“路由”或控制智能体来分派

有了可观测性，这些问题更容易定位到具体是哪一步出了错。

控制成本的三个办法：

  • 用小模型：小语言模型（SLM）在某些场景表现不错，成本低很多。最好先建评估体系，和大模型比一比。简单任务（意图分类、参数提取）用小模型，复杂推理留给大模型。
  • 用路由模型：按请求的复杂程度，把请求分给最合适的模型，简单的给又小又快的，复杂的才用贵的大模型。
  • 缓存回复：找出常见请求，在进入智能体系统之前直接给出回复；还可以用较基础的模型判断新请求和缓存的有多像。对常见问题特别省钱。

智能体协议：MCP、A2A 和 NLWeb

学完这课，你能说清楚 MCP、A2A、NLWeb 三种协议各自解决什么问题、由哪些部分组成、有什么好处，并判断自己业务里的哪一块该用哪种协议。

先搞懂

智能体用得越多，越需要统一的协议来保证标准化、安全，并支持开放创新。原课程讲了三种：

  • MCP（模型上下文协议）：让智能体连接外部工具和数据，完成用户任务。
  • A2A（智能体间协议）：让不同的智能体互相通信、协作。
  • NLWeb（自然语言网页）：给任何网站加上自然语言界面，让智能体能发现并使用网站内容。

MCP 是一个开放标准，用统一的方式给大模型提供上下文和工具，像一个“万能转接头”。你在 Claude Code 课里已经用过 MCP，这里看原课程怎么讲它的结构。它是客户端-服务器架构：

  • 主机（Host）：发起连接的大模型应用，比如 VSCode 这样的代码编辑器。
  • 客户端（Client）：主机里的组件，和服务器保持一对一连接。
  • 服务器（Server）：轻量程序，对外提供特定能力。

服务器提供三种基本能力：工具（可调用的动作，比如“查天气”“购买商品”，服务器会公布每个工具的名称、描述和输入输出格式）、资源（只读的数据或文档，比如文件内容、数据库记录、日志，可以是文本也可以是图片、PDF）、提示（预设的提示模板，用于更复杂的流程）。

MCP 的三个好处：

  • 动态发现工具：智能体能从服务器拿到可用工具清单和说明。传统接口往往要写死集成，接口一变代码就得改；MCP 是“一次集成”，适应性更强。
  • 跨模型通用：MCP 适用于不同的大模型，方便换核心模型比较效果。
  • 标准化的安全：MCP 有标准的认证方式，接入更多服务器时更容易扩展，比管理各种接口的不同密钥和认证方式简单。

原课程的例子：AI 助手（MCP 客户端）连上航空公司的 MCP 服务器，先问“你有哪些工具”，得到“查航班”“订航班”；用户说“查波特兰到檀香山的航班”，助手决定调用“查航班”并传参数；服务器去调航空公司内部的订票接口，把结果返回；用户选好后，助手再调用“订航班”。

A2A 更进一步：MCP 是把大模型连到工具，A2A 是让智能体和智能体通信协作，而且能跨不同组织、环境和技术栈，一起完成共同任务。它的四个核心组成：

组成作用包含什么
智能体卡片像 MCP 服务器公布工具清单那样介绍自己名称、总体任务描述、具体技能清单、当前端点地址、版本和能力（如流式回复、推送通知）
智能体执行器把用户对话的上下文传给远端智能体远端智能体用自己的大模型理解请求，用自己的工具执行
工件（Artifact）远端智能体完成任务后的产出工作结果、完成了什么的描述、文本上下文；发送后连接关闭，需要时再连
事件队列处理更新、传递消息防止任务没做完连接就断了，耗时长的任务尤其重要

A2A 的三个好处：协作更强（不同厂商、平台的智能体能交互、共享上下文，把原本互不相通的系统连起来）；模型选择灵活（每个 A2A 智能体自己决定用哪个大模型）；内置认证（认证直接集成在协议里）。

原课程的例子：用户对“旅行智能体”说“帮我订下周去檀香山的整趟行程，包括机票、酒店和租车”。旅行智能体用自己的大模型推理，判断要找其他专门智能体，就通过 A2A 连接不同公司做的“航空智能体”“酒店智能体”“租车智能体”，分别派任务。它们各用自己的大模型和工具（工具本身也可以是 MCP 服务器）完成各自部分，最后旅行智能体汇总结果，回复用户。

NLWeb 让网站支持自然语言交互。它的组成：

  • NLWeb 应用：处理自然语言问题的核心服务，是网站自然语言功能的“引擎”。
  • NLWeb 协议：和网站做自然语言交互的一套基本规则，用 JSON 返回结果（常用 Schema.org）。目标是给“AI 网络”打基础，就像 HTML 让网上共享文档成为可能。
  • MCP 服务器：每个 NLWeb 部署同时也是一个 MCP 服务器，能把工具（比如 ask 方法）和数据分享给其他 AI 系统，让网站成为“智能体生态”的一部分。
  • 嵌入模型：把网站内容转成向量（embedding），让计算机能按意思比较和搜索。
  • 向量数据库：存这些向量，有人提问时快速找出最相关的内容，按相似度排序。原课程列了 Qdrant、Snowflake、Milvus、Azure AI Search、Elasticsearch 等。

原课程的 NLWeb 例子：旅行网站把航班、酒店、旅游套餐等产品目录用 Schema.org 格式整理或通过 RSS 载入，生成向量存进数据库。用户不用点菜单，直接在聊天框里输入“找一家下周在檀香山、适合带孩子、有泳池的酒店”。NLWeb 把问题交给大模型理解，同时在向量数据库里找相关酒店，再生成自然语言回复。关键是：回复里提到的是网站目录里真实存在的酒店，不会编造。外部的 AI 旅行智能体也能通过 MCP 的 ask 方法直接向这个网站提问，拿到结构化的 JSON 结果。

智能体的上下文工程

学完这课，你能说清楚什么是上下文工程、它和提示工程有什么不同，认出上下文的五种类型，用写入、选择、压缩、隔离等策略管理上下文，并识别中毒、分心、混淆、冲突四种常见的上下文失败。

先搞懂

对智能体来说，上下文决定了它怎么规划、采取什么行动。上下文工程就是确保智能体在做下一步时手里有正确的信息。上下文窗口的大小有限，所以搭智能体的人要建立一套做法，管理信息的加入、删除和压缩。

和提示工程的区别：提示工程关注的是一组静态指令，用规则引导智能体；上下文工程管理的是一组动态信息（包括最初的提示），确保智能体在整个过程中一直有它需要的东西。核心是让这个过程可重复、可靠。

上下文不是一样东西，它来自不同来源，原课程列了五种：

类型是什么说明
指令智能体的“规则”：提示、系统消息、少量示例、工具描述提示工程和上下文工程在这里交汇
知识事实、从数据库检索的信息、积累的长期记忆需要多个知识库时可接入 RAG
工具可调用的外部函数、接口、MCP 服务器的定义也包括调用后拿回的结果
对话历史和用户的持续对话越聊越长，越占窗口空间
用户偏好逐渐了解到的用户喜好和厌恶存下来，在关键决定时调用

先规划，三步：

  1. 定义清楚的结果：回答“智能体做完任务后，世界会变成什么样？”也就是用户最后应该得到什么变化、信息或回复。
  2. 画出上下文地图：回答“完成这个任务，智能体需要哪些信息？”从而找到这些信息在哪里。
  3. 建上下文管道：回答“智能体怎么拿到这些信息？”可以用 RAG、MCP 服务器和其他工具。

管理上下文的六个实用策略（信息流进窗口后怎么主动管；原课程开头把它们概括为写入、选择、压缩、隔离信息）：

  • 智能体便签本（Scratchpad）：在一次会话里记下当前任务和用户交互的相关信息，存在上下文窗口之外（文件或运行时对象），需要时再取。
  • 记忆：跨多次会话存取信息，比如摘要、用户偏好、改进反馈。
  • 压缩上下文：窗口快满时，用摘要和裁剪，只留最相关的信息或删掉较旧的消息。
  • 多智能体系统：每个智能体有自己的上下文窗口，所以拆成多个智能体本身就是一种上下文工程，上下文怎么在它们之间共享和传递也要规划。
  • 沙箱环境：要运行代码或处理大文档时，在沙箱里处理，只把结果和相关信息读回来，不把所有内容塞进窗口。
  • 运行时状态对象：建立信息容器，复杂任务每完成一个子任务就存下结果，让上下文只和当前子任务相关。

检查上下文：用了某个策略后，值得看看下一次模型调用实际收到了什么。一个好用的排查问题是：智能体是加载了太多上下文、加载错了上下文，还是漏了它需要的上下文？

原课程说，回答这个问题不需要记录原始提示、工具输出或记忆内容。上线后更适合记录小的“检查记录”：数量、编号、哈希值和策略标签。比如选择时考虑了多少候选、选中了多少、按什么规则过滤；压缩前后的 token 估计；哪个子任务在独立的智能体或沙箱里跑了；检索到的文档编号和分数；涉及隐私时用编号和哈希，不记敏感原文。目的不是保留更多上下文，而是留下足够的证据，让开发者能看出用了哪个策略、有没有按预期改变下一次调用。

原课程的例子：用户说“帮我订一趟去巴黎的旅行”。

  • 只靠提示工程的简单智能体可能只回：“好的，你想什么时候去巴黎？”
  • 用了上下文工程的智能体在回复之前会：查你的日历看哪天有空（实时数据）、回忆你过去的出行偏好（长期记忆，比如常坐的航空公司、预算、是否只要直飞）、找出可用的工具（订机票、订酒店）。然后回复：“你 10 月第一周有空，要不要按你平常的预算，找 [常用航空公司] 飞巴黎的直飞航班？”

四种常见的上下文失败（原课程都用旅行预订举例）：

失败是什么怎么办
上下文中毒幻觉或错误进入上下文并被反复引用。例：编出一条不存在的直飞航线，之后一直想订这条航线验证和隔离：存进长期记忆前先验证（用实时接口确认航线存在）；发现中毒就开新的上下文线程
上下文分心上下文太大，模型过度关注历史，窗口没满就可能出错。例：聊了很久两年前的背包旅行，问便宜机票时它还在问背包装备定期摘要：只保留当前日期、目的地等相关部分，丢掉不相关的旧对话
上下文混淆多余的上下文（常见是工具太多）导致乱调工具，小模型更容易出现。例：问巴黎市内怎么走，它去调订机票管理工具配置：把工具描述存进向量数据库，用 RAG 只挑最相关的几个（原课程提到研究认为少于 30 个更好）
上下文冲突上下文里有互相矛盾的信息。例：先说坐经济舱，后改成商务舱，两条都留着修剪和卸载：新指令推翻旧指令时删掉或明确覆盖旧的；或者用便签本先理清矛盾再决定

智能体的记忆

学完这课，你能分清工作记忆、短期记忆、长期记忆以及角色、情景、实体记忆等几种类型，说清楚记忆怎么生成、存储、检索和遗忘，并理解“知识智能体”怎样让智能体越用越好。

先搞懂

原课程的定义：智能体的记忆，是让它能保留和回想信息的机制。这些信息可以是一段对话里的细节、用户的偏好、过去做过的动作，或学到的规律。

没有记忆的 AI 应用是“无状态”的：每次交互都从零开始，智能体会“忘掉”之前的上下文和偏好，用户只能一遍遍重复，体验很差。

为什么记忆重要：智能体的聪明程度，和它能不能回想、利用过去的信息紧密相关。有了记忆，它可以：

  • 会反思：从过去的动作和结果里学习。
  • 能互动：在一段持续的对话里保持上下文。
  • 能预判也能回应：根据历史数据预判需求，或做出恰当的回应。
  • 更自主：靠存下来的知识，更独立地工作。

做记忆的目的，是让智能体更可靠、更能干。

记忆的类型（原课程用旅行预订智能体举例）：

类型是什么旅行智能体例子
工作记忆当前任务的“草稿纸”，只抓要点：需求、方案、决定、动作记住“我想订去巴黎的行程”
短期记忆只在一次对话（会话）里有效追问“那里住宿多少钱”，知道“那里”是巴黎
长期记忆跨多次对话保留，用于个性化记得 Ben 爱滑雪，因旧伤要避开高级雪道
角色记忆记住自己是谁、该扮演什么角色定位成“滑雪行程专家”，回答保持专家口吻
工作流/情景记忆记住复杂任务里走过的步骤，包括成功和失败上次某航班没票订失败，下次直接换方案或提前告知
实体记忆从对话里抽出人、地点、事物、事件记住“Le Chat Noir 餐厅”，下次主动提出再订
结构化 RAG把邮件、对话、图片里的信息按结构抽取存好从邮件抽出航班的目的地、日期、航司，能答“周二订的去巴黎是哪班”

短期记忆在框架里长什么样：原课程说，在 Microsoft Agent Framework 的 Python 示例里，短期记忆对应 AgentSession，用 agent.create_session() 创建。同一个会话反复用，上下文就一直在；会话结束或程序重启，这些上下文就没了。需要跨会话保留的事实和偏好，要放进长期记忆：通常是数据库、向量索引或其他持久存储。

怎么实现和存储记忆：这是一套“记忆管理”流程，包括生成、存储、检索、整合、更新，甚至遗忘（删除）信息。其中检索尤其关键。原课程介绍了三种做法：

  • Mem0：一个持久记忆层，把无状态的智能体变成有状态的。它分两步：先用大模型总结对话、抽取新记忆；再由大模型决定这些记忆是新增、修改还是删除（更新），存进可以包含向量、图、键值数据库的混合存储。
  • Cognee：开源的语义记忆，把结构化和非结构化数据变成知识图谱（背后有向量支撑）。它同时用向量相似度和图关系，让智能体不只知道哪些信息相似，还知道概念之间怎么关联。
  • Azure AI Search：作为存储和检索记忆的后端，尤其适合结构化 RAG，用你自己的数据让回答更相关、更准确。

让智能体自我改进：常见做法是加一个单独的“知识智能体”，旁观用户和主智能体的对话，做四件事：

  1. 识别：判断对话里有没有值得存下来的通用知识或用户偏好。
  2. 提炼：把要点或偏好总结出来。
  3. 存入知识库：通常存进向量数据库，方便以后取用。
  4. 补充后续提问：用户再提问时，取出相关记忆附加到提问里，交给主智能体（和 RAG 类似）。

两个优化：

  • 控制延迟：先用便宜、快的模型快速判断信息值不值得存或取，必要时才启动复杂的抽取和检索。
  • 维护知识库：知识库越来越大时，把不常用的信息移到“冷存储”，控制成本。

探索 Microsoft Agent Framework

学完这课，你能说清楚 Microsoft Agent Framework（MAF）提供哪些编排方式和生产功能，认出它的核心概念（智能体、工具、线程、中间件、记忆、可观测性、工作流），并能读懂一个用条件分支串起几个智能体的工作流示例。

先搞懂

原课程的介绍：Microsoft Agent Framework（MAF）是微软用来构建 AI 智能体的统一框架，想同时满足生产环境和研究环境里各种各样的用法。它支持五种编排方式：

  • 顺序编排：需要一步接一步的流程。
  • 并发编排：几个智能体要同时完成任务。
  • 群聊编排：几个智能体围绕同一个任务协作。
  • 交接编排：完成一部分子任务后，把任务交给下一个智能体。
  • Magnetic 编排：一个“经理”智能体建立和修改任务清单，协调下属智能体完成。

为了能上生产，原课程说 MAF 还包含四类功能：

  • 可观测性：用 OpenTelemetry 记录智能体的每个动作，包括工具调用、编排步骤、推理过程，并通过 Microsoft Foundry 仪表盘监控性能。
  • 安全：智能体可以原生托管在 Microsoft Foundry 上，带基于角色的访问控制、私有数据处理和内置内容安全。
  • 持久：线程和工作流可以暂停、恢复、从错误中恢复，适合长时间运行的流程。
  • 可控：支持“人在回路”，某些任务可以标记为需要人工审批。

互通性方面：可以在容器、本地和多种云上运行；可以用 Azure OpenAI、OpenAI 等你偏好的 SDK 创建智能体；支持 A2A 和 MCP 这类开放协议去发现和使用其他智能体和工具；还能连接 Microsoft Fabric、SharePoint、Pinecone、Qdrant 等数据和记忆服务。

核心概念一：智能体本身。

  • 创建：定义推理服务（大模型提供方）、一段指令、一个名字。原课程举了 Azure OpenAI、Microsoft Foundry Agent Service、OpenAI、MiniMax，以及通过 A2A 协议接入的远程智能体。
  • 运行：用 .run（一次性返回）或 .run_stream（流式返回）。每次运行还可以单独指定 max_tokens、可用工具，甚至换模型。
  • 工具：可以在创建智能体时给，也可以只在某一次运行时给。
  • 线程：处理多轮对话。可以建一个能长期保存的线程，也可以只在本次运行里临时存在；线程还能序列化存起来，以后再恢复。

核心概念二：中间件、记忆、可观测性。

  • 中间件：在智能体和工具、智能体和大模型之间插一层，做记录或检查。函数中间件夹在智能体和它要调用的工具之间，比如给每次工具调用记日志；聊天中间件夹在智能体和大模型之间，能看到发给模型的消息。代码里的 next 决定是否继续交给下一层或真正执行。
  • 记忆（接第 13 课）：内存存储是程序运行期间存在线程里的；持久消息用来跨会话保存对话历史；动态记忆在运行前加进上下文，可以放在 Mem0 这样的外部服务里。
  • 可观测性：接入 OpenTelemetry，提供追踪（trace）和计量（meter）。

核心概念三：工作流。工作流是完成一项任务的预先定义的步骤，AI 智能体是其中的组件。它还支持多智能体编排和检查点（保存工作流状态）。三个组成部分：

组成作用原课程的例子
执行器收到消息、完成自己的任务、输出消息；可以是智能体，也可以是自定义逻辑查房态的智能体
直接边一对一把消息传给下一个执行器A 做完交给 B
条件边满足某个条件才走这条路酒店没房时，转去推荐其他选择
分支边按条件分到不同执行器有优先权的客户走另一套流程
扇出 / 扇入边一条消息发给多个目标 / 多个结果汇总给一个目标几个智能体并行后汇总
事件工作流开始、产出、出错，执行器开始、完成，发出请求用来观察流程走到哪

进阶用法，原课程列了四个方向：把多个中间件串起来（日志、鉴权、限流）；用事件和序列化给长流程存检查点，以后续跑；对工具说明做 RAG，每次只给相关的工具；用边和条件路由做多智能体交接。

另外，MAF 讲究框架互通：已经用 LangChain 或 LangGraph 写好的智能体，可以作为 Microsoft Foundry 托管智能体运行，由 Foundry 管运行环境、会话、扩容、身份和接口，智能体逻辑仍留在 LangGraph 里。原课程给了两种托管协议：/responses（兼容 OpenAI 的对话接口，推荐大多数智能体先用这个）和 /invocations（自定义 JSON 格式、类似 webhook 或非对话处理）。

部署可扩展的智能体

学完这课，你能为一个智能体选对部署方式，说清楚上线前的评估关卡、扩展和省钱的几种办法，以及为什么高风险动作要加人工审批、MCP 服务器要当作不可信的边界。

先搞懂

原课程开门见山：在笔记本上能跑的智能体，适合学习，但不适合让几千个客户在凌晨三点依赖它。原型和生产用的是同一个循环（推理、调工具、回答），变的是循环外面的一切。原课程说，模型大约只占生产级智能体的两成，另外八成是运营骨架：

关注点原型生产
托管跑在你的笔记本里托管服务，有版本、逐步上线
身份你自己的 az login 登录托管身份，权限按需限定
状态存在内存里，重启就丢存到外部（对话存储、记忆服务）
出错你自己看报错重试、备用方案、告警
成本“就几分钱”每次请求都追踪、路由、缓存、做预算
质量你用眼睛看输出每次发布前自动评估
信任每个动作你都亲自批策略加人工审批，管住高风险动作

三种部署方式（常常组合使用）：

  • 客户端托管：智能体就在你自己的程序里，推理循环由你的服务来跑，前面各课都是这样。适合要完全掌控循环、或把智能体嵌进现有后台的情况；代价是扩展、状态和容错都得自己负责。
  • 托管智能体（Foundry Agent Service）：智能体注册成 Microsoft Foundry 里的一个资源，由 Foundry 跑推理循环、保存对话、执行内容安全和权限控制。适合想要持久、自带可观察性和治理的情况；代价是底层控制少一些。
  • 智能体工作流：把多个智能体和工具组成一张有明确流程的图，可以有顺序步骤、分支、人工审批节点，还能暂停后接着跑。适合一个任务要经过几个专门智能体、或中间要有人审批的情况；代价是零件更多。

智能体的生命周期不是一次性“推上去”，而是一个循环：创建，定版本，离线评估，通过就部署，上线后观察，收集失败案例，再回去改；旧版本按时退役。原课程强调：离线评估是一道关卡，不是事后补的。新版本达不到评估门槛就不许发布；线上发现的失败，再补进离线测试集。

扩展的四个办法：智能体的每次请求可能触发好几次昂贵的模型和工具调用，所以和普通网站不一样。

  • 无状态处理：不在程序内存里存用户状态，对话存到外部，这样任何一台实例都能处理任何请求，加机器就能扩展。
  • 模型路由：简单请求（判断意图、简短事实回答）交给小而快的模型，真正需要推理的才用大模型。可以用 Foundry 的 Model Router，也可以自己写个简单分类器。
  • 响应缓存：很多问题几乎一样，常见问题的答案缓存起来，直接返回，不再调模型。
  • 并发控制：模型服务有速率限制。限制并发数，失败后逐步拉长间隔重试，实在不行就体面地回一句“正在处理”，总比直接报错强。

可观察性：看不见就管不了。Microsoft Agent Framework 原生输出 OpenTelemetry 追踪，每次模型调用、工具调用、编排步骤都是一段记录。导出到 Microsoft Foundry 之后，你可以把一位客户的投诉从头到尾追一遍，观察每次请求的延迟和成本，在错误率或成本异常时提前告警。给追踪加上 customer.tier、routed.model 这类属性，才能回答“大客户是不是太常被分到小模型”这种问题。

省钱的三个杠杆（按效果从大到小）：

  1. 选对模型大小：能通过评估关卡的小模型，几乎总比同样能通过的大模型便宜。用评估来证明小模型够用，而不是出于谨慎默认用最大的。
  2. 按复杂度路由：只有真正需要的请求才付大模型的价钱。
  3. 积极缓存：最便宜的模型调用，是根本没发生的那一次。

原课程说，评估和成本控制是同一件事的两面：评估定出质量底线，路由和缓存让成本尽量贴近这条底线。

企业部署要注意三件事：

  • 治理：托管智能体继承 Foundry 的权限控制、内容安全和审计日志。给每个智能体一个托管身份，只给它需要的最小权限，比如知识库只读、工单接口限定范围。
  • 人工审批：有些动作后果太重，不能全自动，比如退款、删账号、升级给法务。框架支持“需要审批”的工具：智能体提出动作，执行暂停，人批准或拒绝，流程再继续。
  • 生产环境里的 MCP：把每个 MCP 服务器都当作不可信的边界：固定它的版本，用限定范围的身份运行，校验它的输出，绝不把密钥暴露给它。它是一个依赖，要打补丁、审计、限流。

冒烟测试：部署“成功”只说明平台接受了定义，不代表智能体真的在回答。缺依赖、路由配错、连接过期，都可能让部署显示正常却什么都不回。原课程把检查分成三层：每次部署都跑冒烟测试（能不能连上、有没有回应），发布前跑离线评估（够不够好），上线后持续做线上评估（实际表现怎样）。

创建本地 AI 智能体

学完这课，你能说清楚小模型的长处和短处、什么任务适合放在本机跑，看懂一个完全在本机运行、能调用工具和查资料的智能体，并按“敏感程度和难度”设计本地加云端的混合方案。

先搞懂

上一课把智能体扩展到云上，这一课反过来，把它搬到一台电脑上，全程不调用任何云端模型。原课程给了三个理由：

  • 隐私：代码和文件不离开这台机器，提示、片段、客户数据都不出网。
  • 成本：本地运行没有按 token 计的账单。
  • 离线：在飞机上、在保密场所、或者断网时，照样能用。

代价是：你用的不再是云端最强的模型，而是跑在 CPU、GPU 或 NPU 上的小语言模型（SLM）。这一课讲的是在这个限制之内把智能体做好，而不是假装限制不存在。

小模型擅长什么、不擅长什么：云端大模型有几千亿参数，小模型只有几十亿，要装进笔记本的内存里。

  • 擅长：有边界的结构化任务（分类、提取、给一份已知文件做摘要）；调用工具（判断该调哪个函数、传什么参数）；在自己的数据上快速、便宜、私密地反复试。
  • 不擅长：开放式的、要在大量上下文里多步推理的问题；广泛的世界知识。

所以原课程的策略是：让小模型负责调度，让工具去干重活。模型不需要“知道”你的整个项目，只需要知道什么时候去调 read_file 和 search_docs。

Microsoft Foundry Local 是一个轻量的运行环境，在你自己的电脑上下载、管理和提供模型。对这一课最重要的一点：它提供一个兼容 OpenAI 的接口，所以 OpenAI 的开发包和 Microsoft Agent Framework 的 OpenAI 客户端，只要改一下接口地址（base_url）就能用。之前学的构建方法全部照搬，只是地址从云端换成了本机。它还会按你的硬件自动挑合适的模型版本（CPU、GPU 或 NPU）。

硬件方面，原课程说 8 GB 内存是现实的最低要求，16 GB 以上会比较舒服；有 GPU 或 NPU 更快，但不是必需。

为什么选 Qwen：能调用工具才算智能体。很多小模型能聊天，但生成的工具调用常常格式不对、时好时坏。Qwen 模型专门为函数调用训练过，能稳定输出格式正确的工具调用，正是这一点把“本地聊天模型”变成了“本地智能体”。工具调用的流程和你学过的一样，只是全在本机跑：用户提问，模型决定调哪个工具，工具返回结果，模型基于结果作答。

本地 RAG：与其指望小模型记住你的资料，不如把资料存进本地向量数据库，需要时取出相关片段。原课程用 Chroma，它直接嵌在程序里运行，不用另外管服务器。整条链路都在本机：本地嵌入模型，本地向量，本地检索，本地小模型。这和第 5 课的智能体 RAG 是同一个模式。

本地 MCP：MCP 是一种传输方式，不是云服务。MCP 服务器可以作为本机的一个进程运行，把文件、git、数据库查询这类工具提供给智能体，完全离线。但本地不等于自动安全：本地 MCP 服务器拥有你这个用户的权限，你能碰的它都能碰。所以要限定它能访问的范围（一个项目文件夹，而不是整个用户目录），并把它的输出当作需要校验的输入。示例里的读文件工具也做了同样的“沙箱检查”：路径超出项目文件夹就拒绝。

本地加云端的混合方案：本地优先不等于只用本地。成熟的系统按敏感程度和难度来分：

情况在哪里跑
敏感代码或数据，或者离线本地小模型
简单、有边界的任务本地小模型（便宜、快）
不敏感的数据上的复杂多步推理云端模型
云端出故障时的所有请求本地小模型（降级运行）

这就是上一课的模型路由，只不过其中一个“模型”是你自己的电脑。云端不可用时退回本地，智能体只是变弱，而不是直接停摆。
